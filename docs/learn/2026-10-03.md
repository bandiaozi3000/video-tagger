## 1. 「题材『萝莉 且 日常』怎么筛出一千多部」= 后端实例还跑着旧代码，新参数被静默忽略

**现象（用户原话）**：「筛选标签萝莉且日常，萝莉只有 300 多部，为何筛选出 1000 多部」。

**排查（三证，缺一不可）**

1. **数据**：`GET /api/media?genres=萝莉` → 题材「萝莉」= **310** 部、「日常」= **1750** 部，正确交集（AND）应为 **196**。
2. **接口**：`genreMode=AND` 与 `genreMode=OR` **返回同一个数（1864）** → 已经能判定「mode 参数根本没参与查询」。
3. **后端日志原文**（`data/logs/video-tagger.log`）：
   ```
   MethodArgumentTypeMismatchException: Failed to convert value of type 'java.lang.String'
   to required type 'java.lang.Long'; For input string: "17,4"
   ```
   → 旧实例把 `genres` 当**单值 Long/字符串**，逗号串 `17,4` 强转失败。
4. **前端确实发了新参数**（`app.js` `buildMediaUrls.addCommon`：`p.set('genres', …)` / `p.set('genreMode', …)`）→ 排除"前端没发"。

**根因**：前端已经按 v0.32 契约发「多值 + 模式参数」，但 `:8080` 上跑的是**旧后端**。字段名不认识时后端**不会报错**（被忽略或按单值处理），于是结果看起来像算法错。

**解决前后对比（实测）**

| 请求 | 修复前（旧实例） | 重启后端后 |
|---|---|---|
| `genres=萝莉,日常&genreMode=AND` | 1864 | **196** ✓ |
| `genres=萝莉,日常&genreMode=OR` | 1864 | **1864** ✓ |
| `collectionId=1&collectionMode=AND` | 400 / 忽略 | 200 ✓ |
| `year=2018,2024`、`status=WANT,DONE` | 400 / 忽略 | 200 ✓ |

**可迁移**

- 症状像「算法/逻辑错」时，**先问「现在跑的是哪一版」**。本次最贵的两次排查都不是逻辑错，而是**版本错**。
- 后端对不认识的参数**常常静默忽略**（尤其 @RequestParam 可选时），所以「接口 200」不等于「参数生效」——要比对**同一参数不同取值的响应差异**。
- 定位三件套：**接口原始响应 / 后端日志原文 / 前端实际发出的参数**。

**遗留风险**：契约版本自检（后端暴露 `apiVersion`，前端不匹配就横幅提示「后端需要重启」）**未实现**。这是本次暴露出的最大制度缺口 —— 一条横幅能把这次两轮排查压成 0 轮。

## 2. 编辑器候选库筛选浮层「点了弹出来又没了」

**现象（用户原话）**：「候选下拉进度条点击有问题且滚轮滚不动」（第一次）；后续探针暴露出更本质的症状：**面板打开约 0.8 秒后自己关掉**。

**排查过程（关键是别停在第一个结论）**

1. 先修了「浮层自身滚动被当成页面滚动」（见第 3 篇）—— 修完探针仍崩。
2. 怀疑是刚做的 hash 路由回归 → **用 HEAD 版 `app.js` 做二分**：旧版同样打不开 → **排除路由**。
3. 量化时间窗（自写 CDP 探针）：
   ```
   click() 后 600ms: .vt-pop 数 = 1   ← 其实是开着的
   click() 后 800ms: .vt-pop 数 = 0   ← 已经关了
   ```
   → 结论从「打不开」翻转成「打开后自杀」。**同一段代码，量错时间窗会得出相反结论。**
4. 仪器化 scroll 监听，抓到原文证据：
   ```
   +840ms scroll target=vt-film captured=true
   +909/932/954/972/1003ms 同上（连发 6 次）
   ```
5. 根因：时间轴**胶片条 `.vt-film` 会自动跟随播放头滚动** → scroll 冒到 window → 浮层的 `onScroll` 把「别的容器滚动」当成「页面滚动」→ `onClose()`。

**修法**：`onScroll` **只认 document 级滚动**（`target === document || target === document.documentElement`）才关。理由：浮层是 `position: fixed` 锚在按钮上，**只有页面整体滚动才会让它脱锚**；别的容器自己滚不该关。

**行为变化（如实记）**：以前「浮层外的容器滚动」也会关面板，**现在不关了**。探针里那条 `外部滚动(source=vt-scroll) 面板仍打开=true` 正是这个变化，不是失败。

**验证证据**：`.vt-pop=1`；维度 6 项齐（标签/题材/年份/季度/状态/收藏夹）；真滚轮后列表 `scrollTop=240` 且面板仍开；常驻题材加/拒/删三条路径全对；`events=[]`。

**可迁移**：`position: fixed` 浮层的「该不该因滚动而关」判据是**锚点会不会脱锚**，而不是「有没有 scroll 事件」；页面上任何会自动滚动的组件（播放头跟随、虚拟列表、日志尾巴）都会触发这个误判。

## 3. 浮层内滚轮滚不动、拖滚动条点不动（capture 注册的监听扫到自己）

**现象（用户原话）**：「候选下拉进度条点击有问题且滚轮滚不动」→ 用户确认「就是滚动条」。

**根因**：组件里注册的是
```js
window.addEventListener('scroll', onClose, true);   // capture
```
capture 阶段监听时，**浮层自己内部的滚动也会冒到 window** → 一滚就触发 `onClose()`：滚轮被吃掉、拖滚动条拖到一半面板就没了。对照媒体页浮层——**它压根没有这个监听**，所以那边一直正常。

**修法（保原意图）**：来源在浮层内就跳过，只处理外部滚动。顺带对齐媒体页结构：`.vt-pop-body { max-height: 320px; overflow-y: auto }` → **列表自己滚**，搜索框 / 且或开关 / 常驻输入不会被滚走。

**验证证据（用 CDP 派发**真实**滚轮事件，非合成）**：
```
列表可滚=true 高度=263/1636
真滚轮后: 列表 scrollTop=240（期望 >0） 面板仍打开=true（期望 true）
```
（程序化 `scrollTop=200` 只能证明"不关"，证明"滚得动"必须用 `Input.dispatchMouseEvent(mouseWheel)` 的真实事件。）

**可迁移**：给浮层/弹窗加「外部交互就关」的监听时，**必须显式排除自己人**；capture 注册会额外把"自身触发的同类事件"也算进来。

## 4. 「从标签点媒体跳转失败」= 请求竞态 + 模式交集（**两个独立根因，同一症状**）

**现象（用户原话）**：「从标签点击媒体跳转失败」（标签页该标签写着「媒体 19」）。

**根因 ①：`loadMedia` 没有请求序号保护（竞态）**

跳转时**发了两笔请求**：`showView('media')` 自己发一笔**未筛选**的，紧接着跳转又发一笔**筛选后**的。谁后返回谁写网格。探针包一层 `window.fetch` 记录发出/完成顺序与耗时：

```
序4: /api/media/recent?limit=30&offset=0                 ms=313   ← 未筛选（重）
序6: /api/media/recent?...&tagIds=406&tagMode=AND        ms=27    ← 筛选后（轻）
```
轻的 27ms 先画出 **19** 张 → 重的 313ms 后到，把网格**盖成未筛选**（实测 26 张卡）→ chip 上写着「标签 性转」而网格是全库。

修法：`mediaLoadSeq` 序号，`await` 之后**先判序号再写任何状态/DOM**；`catch` 里也要判（否则旧请求的报错会盖掉新请求已画好的结果）。

**根因 ②：跳转没切媒体页的 tab（模式交集）**

媒体页默认 tab 是「最近观看」→ `mediaMode='recent'` → 走 `/api/media/recent?latest=true`（只看看过/打过标记的）。于是「性转」的 19 部**再交一次**，实测 `mediaTotal=1`。

修法：跳转先把 `mediaMode='all'` + 同步 tab 高亮，再设筛选；顺序刻意改成「先设状态再切视图」，让 `showView` 那一笔就带新筛选。

**根因 ③（用户后续要求「清除」）**：跳转只清了收藏夹，年份/题材/格式/搜索词等旧条件仍参与交集 → 结果数会小于标签页显示的数。改为**清掉全部筛选维度 + 搜索框**（含格式 tab 高亮、子分类下拉），**保留 `sort`/`order`**（排序是浏览偏好不是筛选）。

**解决前后对比（实测）**

```
修复前: 两笔请求里有一笔未筛选 → cards=26（未筛选覆盖）/ 或 mediaTotal=1（recent 交集）
修复后: 两笔请求都带 tagIds=406&tagMode=AND → cards=19 currentMediaListLen=19 mediaTotal=19
        跳转后 chips 只剩「标签 性转×」；q/year/genres/collectionId/format/subcategoryId 全空；events=[]
```

**可迁移**

- 一个症状可能有**多个独立根因**，且都会在"修复第一个"之后继续存在 —— 用户说"还是不行"时不要怀疑自己的修法，先继续取证（本次是 ①②③ 三层）。
- 同一个 loader 被并发调用（导航 + 跳转、快速连点筛选）时，**必须有请求序号**；没有的话"最后到的响应"决定界面，与实际意图无关。
- 跳转/深链要**重置"模式类"状态**（tab、视图开关），它们不是筛选条件但会与筛选做交集。

## 5. 「标签池新增标签未生效」= 通用确认弹窗点「确定」也跑了 `onCancel`（潜伏自 v0.24.2）

**现象（用户原话）**：「标签池新增标签未生效」。

**排查**：先排除后端 —— curl 自清理跑通「建词条 → 关联媒体 → 查使用位置 → 反关联 → 删词条」全程 200/204，使用位置立刻出现新关联 → **后端没问题**。再用浏览器探针（**把写请求全部拦成假成功，不碰真库**）分两条路：

```
【已存在词条】→ POST /api/media/{id}/tags {"tagIds":[407]}      ← 正常
【全新词条】  → 弹确认层 [取消 | 新建并打上]，点下去：
                只发了一个 GET，POST /api/tags 根本没发，输入框还留着字   ← 病在这
```

**根因（`static/app.js`）**
```js
confirm-modal-ok → const fn = confirmModalAction; closeConfirmModal(); if (fn) fn();
function closeConfirmModal() { …; if (cancel) cancel(); }   // ← 无条件跑 onCancel
```
点「确定」时先跑了 `onCancel` → `confirmAsync` 的 promise 以 **false** 结束 → `if (!ok) return null` → 「新建词条并打上」整条链在这里断掉。该行来自 `6fca026`（v0.24.2「全站弹窗统一」），**潜伏了很久**。同族的 `promptModal` 没这个问题（它的 `closePromptModal` 不回调 onCancel）。

**修法**：`closeConfirmModal(cancelled = true)`，只有取消路径才回调 `onCancel`；OK 处传 `false`。

**同根因的第二个受害者（推断，未单独跑那条链路）**：导出前「仍有 N 段未准备 → 导出可用版」也是 `confirmAsync` → 以前点「导出可用版」会被当成取消。
**受影响的非 Promise 调用只有一处**（BT 缺源集确认）：它以前点「确定」会先被 `onCancel` 把状态刷成「已取消」，现在不会了。

**验证证据**：修复后
```
【全新词条】POST /api/tags {"name":"探针临时新词QQ"} → FAKE 200
           POST /api/media/11355/tags {"tagIds":[99999]} → FAKE 200
           refreshMediaDetail 的 GET 一串；输入框清空
```

**可迁移**

- **断言类 API 的"取消/确定"必须分别验证** —— 只看"能关掉"会放过这种「两个分支都跑错那个」的 bug。
- 排查破坏性链路时，**拦下写请求返回假成功**是干净做法：能验证前端的请求装配与后续刷新，又不碰真数据。
- 无效的 catch-all 回调（`closeX()` 里无条件跑 `onCancel`）是典型的"两个调用方共用一个收尾函数"埋雷。

## 6. 写后端门禁时的两类"假信号"（按位映射 / 断言空转）

**背景**：媒体页分组需要列表行带 `season` / `genresJson` / `collectionIds` 三个新字段，于是给 `MediaSummary`（**record**）末尾加了三个字段。

**假信号 ①：record 是"按位映射"的**

`MediaSummary` 的头注释就写着：
> ⚠️ 构造器按位映射：record 参数顺序必须与 MediaMapper 各 SELECT 列顺序一致，中间加字段要同步调整，否则 MyBatis 按位错配（字符串塞进 Long 等）。

→ 加字段必须同步**全部 4 条卡片查询**的列顺序（`listSummaries` / `listByLatest` / `listByCollection` / `listFiltered`），而**编译期看不出来**。新字段统一追加到列尾（定义成常量 `GROUP_KEYS_COL` 挂在 `TAG_NAMES_COL` 之后），并用新 IT 钉住。

**假信号 ②：断言根本没跑到被测行（假绿）**

第一版 IT 就"通过"了 —— 因为 `listByLatest`（最近观看）**只收打过标记的媒体**，而我播种的媒体没有片段 → 那行数据压根不在结果集里 → `assertNotNull(hit)` 之外的字段断言**空转**。

修法：给被测媒体挂一个片段（`clipService.save(...)`）后才算真断言。

**验证证据**：`mvn -o test -Dtest='MediaSummaryTagColumnIT,MediaSummaryGroupKeysIT,MediaFilterMultiIT,MediaServiceIT,CoverServiceIT'` → **27 passed / 0 failed**。

**可迁移**

- 新增字段前**先看这个类型是不是按位映射**（record / 位置参数构造）。是的话"只改一条 SQL"必然埋雷。
- 写门禁时要问一句：**「如果被测行为坏了，这条断言会红吗？」** —— 数据没进结果集、条件把行过滤掉了，都会让断言绿得毫无意义。稳妥做法：**先让断言红一次**（故意写错/临时注掉实现），确认它真的会响。

## 7. 名字撞车：同名函数覆盖 与 路由段冲突

**① 函数同名覆盖（我埋的）**

重构时把时间线的入口拆成「入栈 + 加载」两个函数，新函数也起名 `renderTimeline`：
```js
async function renderTimeline(v) { … await renderTimeline(clips) … }   // 我新写的
function renderTimeline(clips) { … }                                   // 文件里早就有的（画主体）
```
JS 里**后声明的函数声明会覆盖先声明的** → 实际调用的是 `(clips)` 那个 → 传进去的 `v` 是对象 → `clips.map is not a function`。

**报错原文**（探针抓到的客户端异常）：
```
TypeError: clips.map is not a function
    at renderTimeline (app.js:2000:37)
    at openTimeline (app.js:1973:11)
```
修法：新函数改名 `loadTimeline`（与文件里既有的 `loadMediaDetail` / `loadEpisodeDetail` 命名一致）。

**② 路由段冲突（同类问题的另一种形态）**

hash 路由里 `#/media`（媒体页）与 `#/media/2130`（媒体详情）**共用一个段名**。初版 `parseHash` 先遍历详情路由 → 命中 `media` 段但发现没有参数 → 返回 `null`（当成非法）→ **整个媒体页的导航回落成搜索页**；连带"点卡片进详情"的探针报错（因为页面根本没切到媒体页）。

修法：**无参数视图优先判定**（`parts.length === 1 && ROUTE_VIEWS.has(seg)`），`#/media/` 带尾斜线仍算非法（不静默兼容）。

**可迁移**

- 命名空间冲突有两类：**同文件同名函数覆盖**（静默、只在运行时炸）与**路由/键的段名复用**（静默、表现为"跳错页"）。两者都不会有编译或语法报错。
- 加同名函数前 **grep 一遍文件名**；设计路由表时让"集合页"和"详情页"**共享段名但要显式处理"有无参数"两种形态**。

## 8. 探针/脚本工具自身的坑（这次栽得最多的一类）

排查靠自写 CDP 探针（`scripts/probe-browser.mjs` 同款），工具本身出过这些问题，**每一条都会伪装成"业务 bug"**：

| # | 坑 | 表现 | 教训 |
|---|---|---|---|
| 1 | **python heredoc 在本机静默失效** | 补丁脚本打印 `ok`/`patched`，回过 grep 却发现文件**没变** | 改文件一律用编辑工具（精确匹配），不要用 heredoc + `str.replace` |
| 2 | **固定端口被上次残留的 Chrome 占住** | 探针报「Chrome 没起来」（且没有任何提示性错误） | 每次换端口；或先 `netstat` 查占用；**别盲目 kill 所有 chrome**（可能含用户自己的浏览器） |
| 3 | **解包太脆** | 页面里一个异常 → `evaluate` 返回 `{err}` → `JSON.parse(undefined)` 直接把探针炸掉，看不到错误本身 | 解包要容错并**原样打印**返回对象；异常优先显示 |
| 4 | **`.click()` ≠ 真实鼠标三段事件** | 合成 `click()` 能开面板；再补 `mousedown/mouseup/click` 会把面板**再关一次**（切换语义） | 要知道自己的合成事件触发了什么；验证"能不能点开"和"点开后又点了什么"是两件事 |
| 5 | **量错时间窗** | 600ms 看是"开着"、800ms 看是"关了" | 结论性断言必须写清**采样时刻**，并对同一现象取多个时间点 |

**可迁移**：探针/脚本是排查工具，它自己也会给出**假证据**。凡是"结论与直觉相反"的，先怀疑量具：路径对吧？端口对吧？事件类型对吧？采样时刻对吧？控件真的点到了吗？

## 9. 一条给 AI 自己的教训：「零后端改动」不能凭结构猜

**事件**：我评估"媒体页分组"时先说了「**零后端改动**（前端全量拉 + 前端分组）」，用户据此选了方案。**开工后实测才发现**列表行只有 `id/title/year/mediaFormat/subcategory/…/tags`，**缺 `season` / `genres` / `collectionIds`** → 题材/季度/收藏夹三维**根本分不了组**，必须补 3 个列表字段（且要重启后端）。

```
实测（curl /api/media?limit=6000）：
  列表行字段 = id,title,year,mediaFormat,subcategory,subcategoryId,status,rating,coverPath,
               confirmed,source,clipCount,latestAt,collectionCount,fallbackCoverPath,
               externalCoverUrl,tags
  拥有 genres 字段的行数 = 0 / 5248     ← "能不能前端分组" 的决定性事实
  拥有 collectionIds 的行数 = 0
  全库拉取：5248 部 = 1.9 MB / 1.89 s（默认分页 30 部 = 11 KB / 0.056 s）
```

**可迁移**：**"改动面"是实测出来的，不是推断出来的。** 说"零后端改动"之前必须把**数据形状**验一遍（字段在不在、字段是什么格式）—— 本次如果先 curl 一眼，就能在给方案前把"需补 3 个字段 + 重启后端"讲清楚，而不是让用户按错误前提选方案。

**同批另一条**：说"前端全量拉没问题"之前也该先量体积/耗时（上表就是补量的），否则"零改动"等于把成本藏在后面。

## 通用规律（跨条目）

| # | 规律 | 出处 |
|---|---|---|
| 1 | **先确认"你看到的是哪一版在跑"**：版本/时序错常常伪装成逻辑错 | 第 1、4 篇 |
| 2 | **"接口 200" ≠ "参数生效"**：不认识的参数会被静默忽略；要比对同参数不同取值的响应差异 | 第 1 篇 |
| 3 | **量具先自检**：路径 / 端口 / 事件类型 / 采样时刻 —— 探针自己也会给假证据 | 第 2、8 篇 |
| 4 | **一个症状可能有多个独立根因**：修完第一个仍不行是常态，继续取证而不是怀疑修法 | 第 4 篇 |
| 5 | **并发 loader 必须有请求序号**，否则"最后返回的"决定界面 | 第 4 篇 |
| 6 | **破坏性链路的排查要拦下写请求**（假成功），不要拿真实数据做实验 | 第 5 篇 |
| 7 | **门禁测试要能红**：数据没进结果集 / 条件过滤掉了行 → 断言空转 = 假绿 | 第 6 篇 |
| 8 | **按位映射的类型（record）加字段，必须同步所有查询的列顺序** | 第 6 篇 |
| 9 | **"改动面"是实测出来的**：下"零改动"结论前先验字段与数据形状 | 第 9 篇 |
| 10 | **复用别人的机器前，先跑它的老场景当回归** | 媒体页分组（泛化收藏夹分组三件套后跑收藏夹回归 ✓） |
