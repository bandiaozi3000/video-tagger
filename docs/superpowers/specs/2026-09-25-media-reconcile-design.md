## 1. 目标

把本地 `media` 与 Bangumi 的关系梳理干净：

1. **已关联** Bangumi 的 media → 不动。
2. **未关联**且**有引用或人工痕迹**的 → 尽量关联到 Bangumi（用户的原始意图）。

## 4. ⚠️ 实测推翻的两个前提（动手前必须知道）

用户方案隐含假设：「未关联的 media 能自动找到对应的 Bangumi 条目」。**这条不成立**，两条路我都量了。

### 4.1 标题精确匹配：**8%**

12 个抽样，只有 1 个「唯一精确命中」，11 个**连精确命中都没有**。
根因**不是歧义，是两套中文译名**：本地用的是导入源那套，Bangumi 的 `name_cn` 是另一套。

### 4.2 封面指纹：**不可用**（我提的方案，被自己的实验否掉）

原理可行：本地封面确实来自 Bangumi —— media 1889 的本地封面 vs Bangumi 545917 官方封面，aHash 汉明距离 **5**（不相干图 37）。

但**落到批量就不成立**（`/m/` 缩略图 7.6KB，8 个真实样本）：

| 本地媒体 | 最近候选距离 | 次近 | 判定 |
|---|---|---|---|
| 关于我转生变成史莱姆这档事第四季 | 29 | 29 | ✗ |
| 描绘直至生命尽头（正解：画完这个再去死） | 25 | 25 | ✗ |
| 躲在超市后门抽烟的两人（正解：在超市后门吸烟的二人） | 21 | - | ✗ |
| 无自觉圣女今天也无意识地释放力量 | 26 | 26 | ✗ |
| 与奔跑在透明之夜的你… | 37 | 37 | ✗ |
| 虽然我不是完美恶女… | 39 | 39 | ✗ |
| 被遗弃圣女… / 转学后班上的… | 无候选 | - | ✗ |

**0/8 可匹配。** 同一张图是 3–15，不相干图是 37，而这批最近距离 21–29 ——**落在无法判定的灰区**。

两个独立的致命原因：

1. **有些本地封面与 Bangumi 当前默认封面不是同一张图。** 实例：media 1885（史莱姆第四季）的本地封面是 Rimuru+露米娜斯那张，Bangumi 515594 的默认封面是另一张 —— 两者距离 **45**，是全部候选里**最远**的，而「第一季」才是最近的（24）。
2. **同系列不同季的封面两两距离只有 26–47**（实测 28 对），**即使匹配上也无法区分季度**。

结论：**封面只能做粗召回/排序，不能做判定。**

### 4.3 标题相似度闸门：能挡误判，但抓不到真重复

用「Bangumi 返回的候选里存在**本地已关联**条目」(`matchType=EXTERNAL_ID`) 做重复信号，40 个样本：

| 判定 | 数量 | 说明 |
|---|---|---|
| 命中本地已关联 | **26** | 其中**有明显误判**：「轻松熊 → 摇曳百合」「无自觉圣女 → 无敌看板娘」 |
| 仅标题精确 | 5 | — |
| 无任何命中 | **9** | Bangumi 没召回，或 top20 里没有已关联条目 |

**不加闸门的准确率 ≈ 77%（20/26），误判 6 条 = 23%。** Bangumi 关键词搜索太宽（12 个抽样里 8 个返回 ≥20 条），20 条里混进不相干的已关联条目就会触发误判。

加归一化标题相似度（全角/半角、`第N季`↔`第N部分`、标点、数字）后：

| 闸门 | 过闸数 | 精确 | 漏掉的**真**重复 |
|---|---|---|---|
| ≥0.8 | 10 | ~100% | **8 条**（含「描绘直至生命尽头 ≈ 画完这个再去死」相似度 **0.00**） |
| ≥0.4 | 16 | ~87%（1 错） | 2 条 |

### 4.4 ✅ 别名匹配：把可自动关联率从 8% 拉到 82%（用户 2026-09-25 提醒）

**用户的质疑救了这个方案**：「根据标题查不到的能通过别名去识别吗？」

**实测：能，而且几乎零成本。** Bangumi `/v0/search/subjects` 的响应**本身就带 `infobox`**：

```
搜索「画完这个再去死」→ id 545917
顶层字段: date,platform,images,image,summary,name,name_cn,tags,infobox,rating,...
infobox.别名 = [{"v":"描绘直至生命尽头"},{"k":"Netflix","v":"畫完這個再去死"},
              {"v":"Kore Kaite Shine"},{"v":"Draw This, Then Die!"},{"v":"画完这个就去死"}]
```

→ 本地标题「描绘直至生命尽头」**就是它的别名之一**（之前对 `name_cn` 相似度是 0.00）。
并且 `BangumiMetadataProvider.parseSubject` **早就在解析这个「别名」键**（`record.aliases()`），不用新增任何请求。

**同一批 40 个样本，把候选的 `name_cn + name + infobox别名` 全部纳入比对**：

| | 只看 `name_cn`/`name` | **加上 infobox 别名** |
|---|---|---|
| 精确命中 | 8%（1/12） | **29/40 = 72.5%** |
| 相似 ≥0.8 | — | +4 = **82.5%** |
| 抓不到 | 多数 | **7/40 = 17.5%** |

关键修复：

| 本地标题 | 旧结果 | 新结果 |
|---|---|---|
| 描绘直至生命尽头 | 相似度 0.00，抓不到 | **精确命中**「画完这个再去死」（别名） |
| 轻松熊 | **误判**成「摇曳百合」 | **精确命中**「轻松熊」 |
| 北斗神拳 拳王军杂兵们的挽歌 | 0.81 → 错配「…挽歌 **第二季**」 | **精确命中同名** |
| 入间同学入魔了第四季 | 无命中 | **精确命中** |
| 关于我转生变成史莱姆这档事第四季 | 无命中 | **精确命中** |

**连带收获：§4.3 那个「同作品不同季」风险基本消失** —— 因为判定从「相似度最高的已关联条目」改成「**名字或别名精确相等的条目**」，本质是另一个判定。

**剩下的灰区（<0.8，7/40）**：0.79 / 0.78 / 0.75 / 0.67 / 0.67 / 0.31 / 0.11。
其中「斗球儿**弹子** → 斗球儿**弹平**」(0.80) 存疑（可能是本地数据错字），所以 **0.8–0.95 这一段仍需年份+集数校验或人工**。

## 5. 修正后的动作分层（这是本规格的核心）

判定顺序（**一次搜索，三种去向**）：

```
对每个未关联 media A（只扫未关联，已关联不动）
│
├─ 1. 用 A.title 搜 Bangumi（limit 20，一次请求）
│
├─ 2. 在候选中找「**精确命中**」：候选的
│      name_cn / name / nativeName / **infobox 别名** 归一化后 == A.title
│      · 恰好 1 个 → 高置信（①）
│      · 多个      → 用 **年份 + 集数** 消歧（拍板 1B）
│      · 0 个      → 退到相似度 ≥0.8 取最高，并要求年份一致 → ② 人工确认
│
├─ 3. 高置信命中后，用命中的 external_id 查本地 external_work：
│      · **已在本地关联** → MERGE（A 合并进那条已关联 media）
│      · 不在          → LINK（A 新建 external_work 关联）
│
└─ 4. 完全命中不了 → ③ 人工 CSV
```

**注意**：不再用旧的 `matchType=EXTERNAL_ID` 信号（它导致 §4.3 那些误判），
而是「**名字/别名精确相等**」——更严也更准。

层次预估（基于 40 样本：精确 72.5% / 相似≥0.8 10% / 抓不到 17.5%）：

| 层 | 内容 | 1849 上预估 |
|---|---|---|
| ① | 精确命中 → 自动 MERGE 或 LINK（带年份+集数校验） | **~1340** |
| ② | 相似 0.8–0.95 → 人工确认 CSV | **~185** |
| ③ | 抓不到 → 人工挂载 CSV（保持未关联） | **~325** |
| ④ | 无引用无人工痕迹（3464 条）→ PURGE | **3464** |

> ④ 那 3464 条里也可能有重复品，但收藏夹/备注/标签**全空** → 合并零增益，**直接删**。

## 7. 可复用脚本 + 「全量同步」入口

### 7.1 形态

- 后端：`MediaReconcileService`（纯逻辑）+ `MediaReconcileJobService`（任务与进度）
- 接口（挂在 `/api/media/reconcile`）：
  - `POST /plan` → **干跑**，返回三分 + ①②③④ 分层报告（**不写库**）
  - `POST /start` → 后台执行（`dryRun` / `live` 两种模式）
  - `GET /job/{id}` → 进度（阶段、已处理/总数、关联/合并/删除/失败计数、当前项）
  - `POST /job/{id}/cancel` → 取消（在批次边界停）
  - `GET /job/latest` → 最近一次结果（供「上次对账」展示）
- 前端：同步番剧弹窗加 **「全量同步」** 按钮 → 起任务 → 复用现有**底部 pill** 显示进度、点击回到弹窗；完成后结果落进「上次同步」那种持久化块。
- **幂等**：跑第二遍应产出 0 变更（已关联的不动、已删的不存在）。
- **限流**：Bangumi 请求沿用现有 `REQUEST_DELAY_MS=150` + `MAX_ATTEMPTS=3`；图片走 `lain.bgm.tv`，独立节流。

### 7.2 任务持久化（复用现有先例）

模仿 `video_export_task` + `ExportTaskRecovery`（重启后把 RUNNING 标记为 INTERRUPTED）：

新表 `media_reconcile_job`（MySQL Flyway **V39**，SQLite 侧按 §13 冻结不维护）：

```
id, mode(dry|live), status(PENDING|RUNNING|DONE|FAILED|CANCELLED|INTERRUPTED),
phase, total, done, linked, merged, purged, skipped, failed,
message, detail_json, started_at, finished_at, updated_at
```
