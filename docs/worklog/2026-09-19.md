## 增量一：预览 BGM「同一小段反复重放」根因与修复（用户指令：「改」）

### 现象（用户原话 + 我的复述）

- 用户原话：预览页里，音乐播放时"假如歌词是 12345，他会 12 12 然后 23 23 这样播放"。
- 复述：同一小段被**反复重放**，且重放的位置逐次前移 —— 不是简单的整曲循环，是"往回倒一小截"。

### 复现与探针（真实编辑器页 + 无头 Chrome）

- 加载物：`data/recommend-previews/cd882d81-27c0-4d40-b042-2858ff586db5/bgm-0.flac`（4:32.90，272.9s，44.1kHz 立体声，内嵌 mjpeg 封面流）；编辑器草稿：ids `[7130,7338,6917]`、时长 10/5/5/10/5、perScreen 1、style chapter、**无片段**（`mediaClips {}`）。
- 采样方法（页内，每 100ms 一条，避免 puppeteer 往返误差）：`{performance.now(), 播放器帧(读 .vt-transport 文本), audio.currentTime}`，跑 10–12s，统计**帧钟速率**、**音频推进速率**、**currentTime 倒退次数**。
- **实测（修复前基线）**：帧钟 **19.9 fps = 0.664× 实时**；音频 0.70×；**回跳每 ~2s 一次，每次 −0.55~−0.60s**，且表现为连续 6 个采样点各退 ~0.1s（即一串小倒退，不是一次大 seek）。
- **实测（排除项，全部否掉）**：
  - 纯 `<audio>` 播同一 URL（无 Remotion）：`duration=272.9`、单调前进 12.5s/12.5s、**0 回跳** → 不是文件/HTTP/Range（`Range` 请求返回 206 + `Accept-Ranges: bytes`）。
  - 摘掉草稿里的背景图后：20.0 fps（0.667×）、回跳照旧 → 不是背景图。
  - **无 BGM 空跑**：20.1 fps（0.672×）、无音频元素 → 帧钟本身就慢，**不是音频引起的**。
  - `audio.playbackRate = 1`、`preservesPitch` 默认、页面 rAF **60fps**（空白页 57.7 / 编辑器页 60.3）、ducking 窗口 **0**（本次无片段）、page errors 仅 favicon 404。

### 根因（一行）

`backend/remotion/editor/main.tsx` 的 `<Player inputProps={{ input: rendered.input }} />` —— **每次渲染都是新对象字面量**；而编辑器在 `frameupdate → setFrame`（`main.tsx` 帧游标 effect）下**每帧重渲染**。Remotion 侧 `actualInputProps = useMemo(() => inputProps, [inputProps])` → `config` 反复重建 → `use-playback.js` 的播放循环 `useEffect`（依赖数组含 `config`）**每帧重启一次**（`startedTime = performance.now(); framesAdvanced = 0`）→ 时钟每次只能前进"自上次重启以来"的帧数 → **帧钟塌到 ≈ 编辑器重渲染频率（~20fps，0.65× 实时）**。

`<audio>` 元素是按**真实时间**走的 → 相对画面每秒超前约 0.33s → 越过 Remotion 的同步容差（`DEFAULT_ACCEPTABLE_TIMESHIFT_WITH_AMPLIFICATION = 0.65`，见 `use-media-playback.js`）→ 触发 `seek-due-to-shift`，把音频**往回拖 ~0.6s** → 听感就是"刚听过的那一小段又重放一遍"，如此往复。

### 对照实验（隔离探针，同一合成 + 同一 FLAC，证明因果）

探针：`backend/remotion/probe/bgm-probe.tsx`（`?churn=<ms>` = 父组件每 N ms 重渲染，`&stable=1` = 候选修复）。驱动：`.tmp/bgm-probe-run.mjs`。

| 场景 | 帧钟 | 音频推进 | 回跳 |
|---|---|---|---|
| 父组件不重渲染（对照） | 30.0 fps（0.999×） | 1.000× | 0 次 |
| 父组件每 100ms 重渲染 | 23.2 fps（0.774×） | 0.762× | 22 次 |
| 父组件每 50ms 重渲染 | 19.4 fps（0.648×） | 0.637× | 34 次（每组连续 6× ~0.1s） |
| 同上 + `inputProps` 用 `useMemo` 稳定引用 | **30.0 fps（1.000×）** | **0.999×** | **0 次** |

### 修法

1. `backend/remotion/editor/main.tsx`：`inputProps` 提为稳定引用（带注释说明为什么不能用字面量）
   ```tsx
   const playerInputProps = React.useMemo(
     () => ({ input: rendered?.input as MultiMediaPocInput }),
     [rendered?.input],
   );
   // <Player ... inputProps={playerInputProps} ... />
   ```
   `rendered` 可空：`Player` 只在 `rendered !== null` 时渲染，故用 `as` 断言占位。
2. `backend/src/main/resources/static/index.html`：缓存戳 `v=20260918-v029ui8` → `v=20260919-v029fix1`（否则用户浏览器吃旧 `editor.js`），并 `cp` 到 `backend/target/classes/static/index.html`（本机 8080 从 `target/classes` 取静态资源）。
3. `backend/remotion` 下 `npm run build:editor`（`dist-editor/` 走 `file:` 资源 handler，**不需要重启后端**）。

## 增量九：结构设计（"多部推荐 + 每部带片段"该怎么排）

**用户问题**：当前场景是"推荐多部影片，每部介绍时携带片段"，这种场景怎么弄更好？

**我的判断**：问题不在单帧美观，而在**"介绍"与"片段"被做成了两个平级场景**（`MEDIA_INFO` → `MEDIA_CLIP`）——后果：① 有片段的部要先看一屏静态卡片才见画面，节奏断；② 没片段的部只剩卡片；③ 连续 N 部长得一模一样（同模板套图）。

**方案：把"一部"做成一个节拍单元**：`片名卡（1.5s）→ 画面/片段（6–9s）→ 硬切进下一部`；信息不再独立占屏，压成画面上的 **lower-third**（片名·年份 + 一句推荐语）。依据：预告片/混剪的通行做法（Apple TV+ sizzle、Netflix Next on Netflix、Aniplex 季番 PV 都是"标题卡 + 画面流 + 小字幕"，没有"资料页"这种物）。

**三条硬规则**：
1. **有片段的部不再出资料页**——片名卡之后直接上画面；
2. **同一部的多个片段之间不插全屏卡**，硬切 + 只换集号小字 → 连成一段"能看下去的画面"（沉浸感来源）；
3. **无片段的部用"封面镜头"顶上**（封面出血 + Ken Burns + 右侧留白承载信息），在时间轴上与片段段占同样节拍，整片不一停一顿。

**实现代价**（评估，未实施）：`scene-plan.ts` 一处判断（该部有片段 → 跳过 MEDIA_INFO）+ 片段场景内部加 1.2s 片名卡前置 + 移除常驻 chrome（Topbar/Trackbar/BgmBadge）；转场用下一部主色做 `clip-path` 色带擦除（零新依赖）；**不动 Java**。

**交付**：`docs/design/2026-09-19-recommend-video-structure.html`（分镜表 + 11 格真 1280×720 舞台）+ 11 张截图 `…-structure-*.png`。

**自检**（像素实测，11/11 面板）：控制台 0 错误、0 请求失败；片名卡底色 rgb(52,27,25)/rgb(29,43,36) 分别对应 7492 暗红与 5609 战车绿（每部一色生效）；封面镜头左亮 152 / 右 39（出血 + 留白的不对称成立）；**色带满屏帧 rgb(250,215,168) = #fad7a8，与芙莉莲封面实测取色完全一致**（转场色带用的就是下一部的主色）。

## 增量十二：开屏从「闪回」改为「速览矩阵」（用户换思路）

## 增量十三：速览段从「网格」改为「扇形」（用户：网格太死板）

**用户反馈**：排版过于死板，想要"一个个闪回，最后类似扇形那样呈现"。

**改法**（仍只动 `src/cinema/`）：`SCAN` 幕的布局从"网格一次铺开"换成**逐张飞入 → 落成扇形**。

- **扇形数学**：卡片中心沿圆弧排布 `x = cx + R·sin θ`、`y = cy + R(1−cos θ)`，`θ` 在 ±30° 间均分；`R` 由目标弧宽（画幅宽 62%）反解 → 张角越大边缘越低，读起来像"摊开的一把牌"。
- **逐张飞入**：每张错峰 3 帧，从下方 74px 带旋转过冲飞入（spring），落位后**扇形再缓慢张开一点**（21.6° → 30°）——静止的扇形也会继续"呼吸"。
- **层次**：中心卡最大（scale 1.0）最亮（brightness 1.0）且 z-index 最高，两侧按弧度衰减到 0.9 / 0.66；卡片间用 1px 画布色描边分隔（不用阴影，守住"零发光"的约定）。
- **清单超过 12 部**：后面叠一层**后排扇形**（0.84× 尺寸、brightness 0.42、张角多 6°），剩余部数以"＋ 还有 N 部"标出——保住"清单很大"的印象。
- 保留上一轮的高光横扫 + 年份标签依次点亮（被扫到的年份由 55% 白变纯白）。

**实测**（12 部真数据，frames 0–239 = 8s）：
- 像素审计逐帧：`f1` 内容只在左中 → `f2` 覆盖 4 条竖带 → `f4/f5` **五条竖带内容 47% / 65% / 85% / 82% / 47%**（左右对称、中心最亮）→ 扇形确实铺满且中间最突出；底部（标题/统计）内容 6.6% ✓。
- 成片归档 `docs/design/2026-09-19-recommend-cinema-fan-opening.mp4` + 5 张静帧；旧的网格版静帧/成片已删（避免两份共存）。

## 增量十四：开屏再改为「满幅照片墙」（用户：要照片墙、画面感强、前几版太死板）

**用户反馈**：想要照片墙那种、画面感强；网格版与扇形版都"太死板"。

**我的判断**：网格是"排列"、扇形是"卡片摆在黑底上"——两者都还是**布局**；照片墙是**画面**。画面感的来源是"图把画幅填满"，所以这一版的三条硬指标是：不留白、不留间隔、没有黑底。

**做法**（仍只动 `src/cinema/`，`SCAN` 幕）：
1. **填满**：瓦片 `object-fit: cover` 裁切，行数由"3:4 竖版在 16:9 里最接近铺满"反解（`rows = clamp(round(√(N/2.37)), 1, 5)`），整面墙再整体缩放到 **cover**（`max(画幅宽/墙宽, 画幅高/墙高) × 1.06`）→ 任何部数都不露底；
2. **透视 + 视差**：整墙 `perspective(1500px) rotateX(11deg)`，纵向缓慢推进（scale 1.00 → 1.07），横向 `rotateY` 从 −2.6° 漂到 +2.6°（帧驱动、可复现）；
3. **逐张落下**：每张错峰 2 帧、从上方 26px 落下进入；**亮度按 mediaId 取 5 档**（0.62–0.92）→ 墙有深浅层次，不是一张平板；
4. **标题压在墙上**：底部渐暗 + 暗角（radial 34% → 72% 黑），标题 0.082H + 一行真实数字，最后一道斜向高光横扫（`linear-gradient` 扫过，被扫到的瓦片底部主色线点亮）。

**实测**（12 部真数据，frames 0–239 = 8s）：
- 像素审计九宫格：`w1`（落位中）空 56% → `w2` 空 5.2% → `w3/w4` **空 4.6%，九宫格每一格空 0.2%–8.4%**（= 满幅有内容、无黑边）；全区亮度 52/σ36（有层次）。
- 成片 `docs/design/2026-09-19-recommend-cinema-wall-opening.mp4` + 静帧 4 张；**扇形版与网格版的文件已删**（不留三份共存）。

**仍未变**：定格段、逐部段落、落款、旧模板零改动；`accentColor` 待重启 + webp 解码选项待用户定。

## 增量十五：开篇改为「冲入 · 掠影」（用户：前三版都太死板，要求先查主流设计）

**用户反馈**：网格 / 扇形 / 照片墙三版都"死板""硬套模板"；要求先找相关设计再定怎么设计开篇。

**研究结论（附来源）**——"灵动"由五条机制构成，而我前三版缺的正是这五条：
| 机制 | 依据 | 我前三版的病 |
|---|---|---|
| 速度变化（speed ramp / 甩镜约 0.25s、模糊在中点最强） | impractical.ai、vitelnk time-remapping | 全程匀速，每张都是 2 帧落下 |
| 纵深视差（虚拟相机在 3D 空间移动，而非缩放平面） | focusee、designkkashi | 只有一层，rotateX 是假纵深 |
| 运动模糊与速度成正比、静止才锐利 | compstart（180° 快门约定） | 完全没有模糊 |
| 尺度层级 + 打破网格（尺度差/视觉重量，而非均匀格） | collage 布局实务（单一来源，谨慎采信） | 瓦片全部等大 → 像瓷砖 |
| 编排（预备/跟随过冲/次级运动/错峰/克制） | madegooddesigns、motionly | 每张入场完全一样，无主次 |
另两条元结论（We Design Motion，编辑观点）：模板感来自"设计决策没动过"；以及**统一色彩分级**——原色平铺读起来是一堆截图。

**实现**（只动 `src/cinema/`，`SCAN` 幕）：
- **掠影**：主推先贴脸冲出（scale 2.35→1.15、blur 20px→0），其余 4 张每 0.26s 交替从左上/右下掠过，**模糊 ∝ 速度²**；
- **减速落位**：5 张按尺度差落位（1.0 / 0.74 / 0.6 / 0.5 / 0.44）+ 轻微旋转（-5°~+4°）+ 重叠 + 出血出右缘，**刻意不是网格**；落位用弹簧过冲（低阻尼、有重量）；
- **远景墙**：铺满画幅的恒模糊墙（blur 3px、brightness .5），与近景**反向**漂移 → 真纵深；
- **遮挡交互**：标题层 z-index 在卡片**之下**，主推的"幽灵卡"在 2.4s 左右**横扫穿过画面、遮住标题一瞬**后离场（用独立元素，不动已落位的卡，避免跳帧）；
- **相机**：缓慢推进 1.00→1.045 + sin 驱动的 rotateY/translateX 微漂（"机器是人端的"）；
- **色彩分级**：`mixBlendMode: color` 压一层冷调（0.4）+ 暗角 + 上下压暗 + 柔光横扫（screen）+ SVG `feTurbulence` 确定性颗粒（逐帧平移背景，不需要随机数）。

**实测**（12 部真数据）：取样 5 帧的像素审计——**空 0.0%–1.2%**（每一帧都没有黑底，远景墙始终填满）、**平均色 rgb(78,82,83)**（冷调分级生效，封面原色已被统一）、九宫格空率 0–7%；**帧间运动量 23–35**（持续在动，不是静态排版）。成片 `docs/design/2026-09-19-recommend-cinema-opening-raid.mp4`（10s：掠影 4.2s + 定格 2.8s + 第一张片名卡）+ 5 张静帧；照片墙版产物已删。

**顺手修的一处重复**：掠影段已给过主题标题，定格段原本又给一次 → 改为"有简介时不重出标题（改成大字给简介），无简介才用标题兜底"。

**仍未变**：逐部段落（片名卡/封面镜头/片段/落款）、旧模板零改动；`accentColor` 待重启 + webp 解码选项待定。

- 中缝（46%–58%）压暗一条带，给主题/副标题/引言/统计，两排都不遮它；聚光仍按离中心距离。

**② 修 bug 1「片段一直抖动」**：根因是我给片段加了 `1 + sin(frame/fps·π·0.6)·0.02` 的**往复缩放**（每 3 秒来回放大缩小一次，看起来就是在抖）。改为**一整段极慢的单向推镜**（1.00 → 1.02），那是"镜头在走"而不是"画面在抖"。

**③ 修 bug 2 + 重设计「右下角标」→「左下信息卡」**：根因是卡片在变形结束时被 `opacity: morph < 0.98 ? 1 : 0` 抹掉，所以右下角什么都没有（我加了文字却没有留下卡面）。现在：

## 增量二十一：片段"还在晃"的**真根因**——素材帧率与时间轴不一致（23.976 → 30）

**用户反馈**：改完还晃。**我上一次改的不是根因**（去掉了往复缩放，那是次要因素）。

**排查过程（按可复现的探针走）**：
1. 先列出片段幕里所有逐帧变化的东西：只剩 `morph/ease`（前 0.7s，单调）、`infoText`、以及 `push = 1.00→1.02`（单调，不是往复）→ 代码里已无振荡源。
2. 于是查素材本身：`ffmpeg -i data/recommend-previews/<token>/media/clip-179.mp4` → **`23.98 fps, 23.98 tbr, 24k tbn, 47.95 tbc`**，而推荐时间轴固定 **30fps**。
3. 为什么这种素材能直通：`RecommendClipSourceService.playable()` **只看编解码**（h264+aac → 零重编码复制），不看帧率。

**根因**：23.976fps 素材进 30fps 时间轴 → 每帧按时间取源帧时出现**规律性重复/跳帧**（3:2 节奏）→ 观感就是"一直在晃/抖"。

**修法**（Java，向后兼容）：
- `MediaProbe.fps(file)`：新增帧率探测（ffprobe 优先，回退 `ffmpeg -i` 的 `xx fps`）。
- `RecommendClipSourceService`：新增 `targetFps`（`videotagger.render.fps`，默认 30）；`playable()` 现在要求**编解码可播且帧率与时间轴一致**，不一致就走重编码；`export()` 的 ffmpeg 命令加 `-vsync cfr -r <targetFps>`（本机 ffmpeg 是 2018 版，不支持 `-fps_mode`，故用 `-vsync`）。探测不到帧率时仍按可复用处理，避免探针不可用把全部片段都重转一遍。

**验证（两段对照实验，非估算）**：
- 归一化命令实测：旧 23.98fps/帧间隔 0.0417 → 新 **30fps/帧间隔 0.0333（CFR）**。
- **渲染级 A/B**（同一段素材、同一片段场景、同一内容窗口 2.0–3.5s，各 45 帧）：旧成片 **44 对相邻帧里有 6 对完全相同**（重复帧位置 1,5,14,24,26,44 = 3:2 节奏），新成片 **0 对**（每帧都在推进）。节奏图谱：旧 `·▁▁▁·▁▁▁▁…·▁·▁▁` vs 新 `▁▁▁▁▁▁▁▁▁▁`。
- 门禁：`mvn test` 通过（含更新后的 `RecommendClipSourceServiceTest` 构造器）。
- 产物：`.tmp/clip-30fps.mp4`（归一化素材渲染的片段段，5.2s）、`.tmp/exp-old.mp4` / `.tmp/exp-new.mp4`（ffmpeg 对照）。
