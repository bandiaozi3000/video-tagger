## 增量三：掠影段重做（用户指令：「修改掠影」→ 看过一版后「感觉还是快，能类似于落叶飘动那种效果吗？」）

### 旧实现的三个不连续（读码）

`cinema/scenes.tsx` 的 `RaidCard` 把运动拆成**两段拼接**：

1. 掠入段 `interpolate(raidP, ...)` **纯线性** —— 匀速冲脸，没有预备也没有减速；
2. 交接帧（`arriveAt + raidSpan`）：`scale` 从 `1.15` 突跳到 `slot.s×0.93`，`rot` 从 `slot.rot` 突跳到 `0`；位置连续、速度/缩放/旋转不连续；
3. 模糊用 `(hero?20:16) × (1-settle)²` —— `settle` 是 spring，落位起手速度≈0 却糊得最厉害（模糊与真实速度反相）；
4. 弹簧参数 `damping 200 / stiffness 90` 严重过阻尼（临界阻尼 ≈ 2√90 ≈ 19）→ 没有过冲、收得慢（代码注释写的"弹簧过冲"根本不成立）。

### 第一版修正：一条曲线（快起手 + 微过冲）—— 用户反馈「感觉还是快」

把两段合并成一条 `Easing.bezier(0.15, 0.88, 0.26, 1.05)`，全部属性同源。用户看过后仍觉得快，于是换成**落叶飘动**（本日定稿的那版）。

### 第二版（定稿）：落叶飘动

- 新增 `src/cinema/raid.ts`（纯函数 + 回归测试）：
  - `fall`：`Easing.bezier(0.42, 0.06, 0.21, 1)` —— 慢起手（松手）→ 加速（重力）→ **长软尾**（软着陆）；
  - `sway`：`dir × 0.055w × (1−fall)² × sin(2π·1.25·fall − π/2)` —— 包络 `(1−fall)²` 保证**振幅与速度在落位处同时归零**（末态精确、不会"停一下"）；相位 −π/2 让起手侧向速度为 0（叶子是被松手，不是被甩出）；

## 增量四：落叶第三版 + 封面统一走 Bangumi

### 为什么前两版生硬（用户：「这个飘动效果也太生硬了」）

両版都是"单一数学曲线"，生硬是结构性的：

1. 横向只有**一条正弦、一个频率** → 读起来是"左右摆一下"，不是飘；
2. 下落用单条贝塞尔：中段速度很陡、末段几乎不动 → "吊着 → 掉下去"；
3. 侧倾只有 ±6° 且被 `(1−t)²` 快速收掉，卡片全程基本正立；
4. 五张卡**共用同一条曲线**，只有相位差 → 整组动作像机械装置；
5. **落位即完全静止**（后面几秒一帧不动）→ "落到墙上"。

### 这一版（定稿在 `raid.ts`）

- 横向：**两个不同频率的正弦**叠加（主频 + 2.4× 次频，次频包络更硬），相位 −π/2 使起手侧向速度为 0；
- 纵向：`DESCENT = bezier(0.33, 0.05, 0.26, 1)`（释放 → 接近终端速度 → 软着陆）+ 低频垂荡；
- 旋转：**慢转**（起手预转 ±10° 逐渐转正）+ 与横向速度同相的侧倾；
- 每张卡的主频倍率（0.86~1.14）与相位按 `index` 确定性派生 → 彼此不同步；
- 落位后**微量续飘**：`rest·e^(−3·rest)`（落位帧为 0、起点速度非 0，峰值 ≈5.7px@1280）→ "轻轻贴上去"而不是"撞到墙上"；

```
2026-09-20 13:01:52 [INFO] Watcher started. Scan interval: 30s; backup interval: 60m
```

```powershell
$ErrorActionPreference='Continue'; & docker info --format '{{.ServerVersion}}' 2>$null   # → 不抛，$LASTEXITCODE=1
```

## 增量十五：“被遮挡”的真因 + 确定性抖动（用户：「即使勾选多部，当时显示会被遮挡，而且我看槽位是固定的，能做到偏随机吗？」）

### 被遮挡的真因（几何实测，不是观感）

把上轮我加的陪衬位置套上渲染盒算了一下（`baseH = 0.56h`、`baseW = 0.75·baseH`）：

```
hero 盒:   x 232.8~535.2, y 172.8~576.0        # 1280×720
陪衬 #5 盒: x 297.9~418.9, y  92.2~253.4      ← 完全落进 hero 盒
```

我上一版把陪衬放在 `(0.28, 0.24)`，**正好落在 hero 的盒子里** —— 多勾几部也看不到，就是它。

### “偏随机”的硬约束：必须确定性

Remotion **逐帧并行渲染**（多进程、乱序）——`Math.random()` 会让同一帧在不同 chunk / 重渲时得到不同布局，甚至同一帧内的两个卡互不一致。所以用 `hash01(mediaId, salt)` 派生：**同一部永远同一个位置**，换一部才变。

- 抖动幅度（`slots.ts` 的 `JITTER`，想调只改这里）：位置 `±0.03` 画幅、尺度 `±5%`、旋转 `±4°`；
- **Hero 不抖**：它是构图基准（用户定“第一个就是 Hero”），抖它会让整个画面随換片漂；
- 幅度全部小于手排槽位间距（相邻尺度差 6%~26%），所以“越靠前越大”的关系不被払乱（单测钉住）。

## 增量十六：方案 A —— 中景摆位“真随机”，Hero 硬保护（用户：「A，但是确保 Hero 不变不被遮挡」）

### 先说清约束（为什么不是 `Math.random()`）

Remotion 逐帧**并行**渲染（多进程、乱序），帧内随机会：① 同一帧在不同 chunk 里摆不同位置（拼接处跳位）；② 预览与成片不一致（所见非所得）。所以随机数必须**在渲染开始前定下来**。做法：**种子存进草稿**，沿请求体传到后端，再进 `params.seed` —— 同一份草稿预览与成片完全一致，点一下 🎲 就换一套。

### 实现

**Remotion 侧**
- `params.ts`：新增 `RenderParams.seed`（默认 0）+ `resolveParams` 解析；
- `cinema/slots.ts` 重写：
  - `HERO_SLOT` 常量（Hero 固定 `(0.30, 0.52) s=1.0 rot=-3`）——**Hero 不参与随机**；
  - `cinemaLayout(count, seed)`：其余卡从 4 条**空带**（顶部/右侧/底部/左竖）里摇候选，**碰到 Hero 盒（含 0.02 余量）或自己的中心落进已摆卡里就重摇**（最多 60 次，兜底取“离已摆卡最远”的候选）；尺度封顶 `0.74·0.88^(i-1)` 再在 72%~100% 里摇 → 越靠后越小巧、Hero 永远最大；
  - `cinemaLayoutCached`（逐帧都会问一次，按 `count:seed` 缓存）；
  - 空带的位置是照 Hero 盒（x 0.18~0.42 / y 0.24~0.80）与左下标题区算的，所以随机也不会摇到 Hero 头上或标题上。
- `scenes.tsx`：`const layout = cinemaLayoutCached(heroes.length, plan.params.seed)`，两次 `slotFor(...)` 改成 `layout[i]`；**Hero 仍然最后绘制（在最上层）** —— 就算几何上出意外也不会被压。

**编辑器**

## 增量二十九：素材信息刷新 A+B（用户：「推荐的媒体如果信息有更新的话，现在是不是只有强刷才能看到最新信息？」）

### ① 转场音不生效：**不是 `.wav` 的问题**

## 可迁移的学习点

1. **字体名要实测，不要照抄文件名**：TTF 的 `name` 表里 nameID 1/16 才是 CSS 能命中的族名（`阿里巴巴普惠体 2.0`），文件名/全名（`AlibabaPuHuiTi-2-115-Black` / `阿里巴巴普惠体 2 115 Black`）都不是。探针：在**渲染同一个浏览器**里 `canvas.measureText` 对比"必然不存在的字体"的宽度，同宽即未命中。
2. **"刻意设计"要写清触发时刻**：`Scan` 注释写了"封面会遮住标题一瞬"，但实际定格后 hero 卡底边就贴在标题上 → 用户看到的是"盖住字"。设计意图要标时间窗（帧区间），否则下一个人（或半年后的自己）会把 bug 当设计。
3. **上限型参数 = 假参数**：把用户设置当 `min(上限, …)` 且再叠加常数夹子，用户改大就彻底无感。同一形态里用不到的参数（cinema 的序言/章节时长）应在 UI 上置灰，而不是静静吃掉。
4. **兜底路径要跟主路径走同一套校验**：`base64ForCoverPath` 只认 `/covers/`，于是"片段帧兜底"在成片里静默失效、预览里却正常 —— 两端行为不一致比直接报错更难查。
5. **验证 UI 之外的东西要用同一个运行时**：字体、`staticFile`、`public/` 这些东西只在**渲染用的 headless shell** 里测才算数（普通 Chrome 装了字体也测不出 `public/` 是否进包）。
6. **动画"生硬"先查有没有交接点**：两段拼接（线性掠入 + spring 落位）最容易在拼接帧留下 scale/rot 突跳；把它们换成**同一条曲线派生全部属性**后，连续性可以被单元测试盯住（逐帧增量不得出现孤立尖峰），不必靠肉眼。
7. **"飘"= 两个不同相位的运动叠加**：单条贝塞尔永远读成"位移"，而 sway（正弦）+ tilt（与侧向速度同相）才能读成"飘"。关键技巧：**包络 `(1−t)²` 同时把振幅和速度收到 0**，否则末态要么差一点、要么落地前"顿"一下。
8. **“有没有生效”要用测试钉住，而不是靠注释**：`openingIds` 的注释写着“取到的前 5 部”、实现却是 `slice(0,5)`，这种“注释描述了意图、代码没做”的偏差能潜伏很久；补一条 `expect(plan.scenes[0].mediaIds).toEqual([...])` 就再也不会复发。
9. **判“帧节奏”只能用帧间差，不能用 md5**：h264 重编码会把同内容像素改写 ±1，`md5sum` 判相邻帧相同会得到“全片无重复帧”的**假阴性**（我就是这么把 09-19 的删帧当成修好了）；`tblend=all_mode=difference,signalstats` 的 YAVG 序列才能看出“每 5 帧停一拍”。
10. **“重编码成时间轴帧率”治不了帧率不匹配**：容器帧率变了，内容还是 24 张/秒，重复帧只会换位置不会消失（实测帧间差序列一模一样）。
11. **一个输出文件只能有一个帧率**：“片段原生 24 + 其余 30”在编码层不存在；要么整片统一（24/60），要么插值。确认这个物理约束再报价，能省一整轮来回。
12. **诊断先量“素材”而不是先改代码**：本次真根因由三个 ffprobe/ffmpeg 探针定性（素材帧率、会话缓存帧率、帧间差序列），比再猜一轮 CSS 动画快得多。

## 增量二十三：集行「本地源灯」口径修正（用户：MM一族 第5集有本地源，灯还是红的）

### 现象（在用户正在跑的实例上实测，非推断）

```
GET /api/assets/lights?episodeIds=1413,1414,1415   → 1413 missing / 1414 missing / 1415 missing
GET /api/episodes/1414/material/channels           → {"channel":"C2","state":"PRESENT", file = …MM一族！-旧番主线①-第05集-05.mp4}
```

同一个集，**同一次会话里**：灯说"无本地源"，集详情「本地源/本地回顾」说"在场"。数据库侧证据：`episode 1414` 的 `video_asset` **0 行**；Animeko 缓存文件确实存在（`media-downloads/web-m3u/588fffc9-….MM一族！-旧番主线①-第05集-05.mp4`）；该媒体 12 集里只有第 5 集有这个缓存文件（与用户"只有第5集"一致）；12 集全都没有 `video_asset` 行（所以整排都是红的，只有第 5 集"本该绿"）。

### 根因

`AssetLightsController.lights()` 判「集有本地源」**只查 `video_asset` 表**（AVAILABLE + 文件在场），
而集详情那条路走的是 `EpisodeReviewService.resolve()` —— 它是 **C1 本地资产 → C2 Animeko 整集缓存** 两级。
于是「只有 Animeko 缓存」的集：回顾可用、灯是红的。**两处口径不一致**，不是数据问题。

### 修法

- `EpisodeReviewService.cachedEpisodes(Collection<Long>)`：批量问"这些集里哪些 C2 缓存在场"（桥 → `provider_episode_id` → `AnimekoCacheLocator.locate`）。registry 只有 **10KB**，逐集 locate 足够；将来变大再改一次性解析。
- `AssetLightsController.lights()`：先在原来那一次批量资产查询里算好每集 `hasAsset`，**只对没有资产的集**问 C2；命中则 `state=available` + `via:"animeko-cache"`（资产命中给 `via:"asset"`）。缓存探测异常按"无缓存"处理，不把整排灯打黑。
- 前端 `refreshAllEpLamps`：`via==='animeko-cache'` 时 tooltip 写「本地源就绪（Animeko 整集缓存，可回顾/剪辑）」，免得又有人问"为什么绿了/红了"。

- 单测新增 `EpisodeReviewServiceTest.cachedEpisodesForLights`（无桥的集不入选、有缓存文件的集入选）；全量 `mvn -o test` = **388 tests, 0 failures**。

### 遗留

- 灯现在等价于"能本地回顾"，但**不等于**"有可剪辑的整集源"：Animeko 缓存能被 `ffmpeg` 直接读，剪辑照旧可行，所以这个口径是对的；但如果将来 C2 之外的渠道（远程流）也算"可回顾"，灯要再扩。**未验证**：Animeko 侧同时有 100+ 集的媒体，灯接口的逐集 locate 耗时（当前 registry 10KB、12 集实测无感）。
