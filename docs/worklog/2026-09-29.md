## 增量一 · Animeko 改了 WEB 缓存文件命名（`mediaId.mp4` → `http-v2-{sha256}.mp4`），导致「本地源识别不到」

**用户报**：「当前 animeko 缓存貌似变更策略了。你去看零之使魔-双月骑士，我下载了第 12 集，但是识别不到了。」并给了文件路径：
`%USERPROFILE%\AppData\Roaming\Him188\Ani\data\media-downloads\web-m3u\http-v2-73b20a95fd2079401ccab838451d77bdb046220e4139cb44780b7bf8e0884415.mp4`

### 现象复现（实测，后端 8080 在跑）

```bash
curl -s "http://localhost:8080/api/assets/lights?episodeIds=45331"
# {"episodes":{"45331":{"state":"missing"}},"clips":{}}

curl -s "http://localhost:8080/api/episodes/45331/material/channels"
# {"message":"该集无本地源（无本地资产、无 Animeko 整集缓存）；可先在 Animeko 显式缓存该集","state":"UNAVAILABLE",...}
```

`episode 45331` = 零之使魔 双月骑士（media 8299）第 12 集「诀别的婚礼」，文件**确实在场**（354MB），但 C2 求值 `PENDING/UNAVAILABLE`。

### 排查探针（可复现）

```bash
# 1) registry 里该集的条目：metadata 里只有 subjectId/episodeId，**没有任何 path/file 字段**
node -e 'const j=JSON.parse(require("fs").readFileSync(process.env.USERPROFILE+"/AppData/Roaming/Him188/Ani/data/datastore/mediaCacheMetadataV2","utf8"));
 j.forEach((e,i)=>console.log(i,e.engine,JSON.stringify(e.metadata.subjectId),e.metadata.episodeId,e.metadata.subjectNameCN))'

# 2) 文件名与真实下载 URL 的对应关系只在 Animeko 自己的日志里
grep -o "Preparing to download with id=[^,]*, url=[^,]*, mediaType=[A-Z0-9]*" \
  "$USERPROFILE/AppData/Roaming/Him188/Ani/data/logs/app.log"
# http-v2-73b20a95…  url=https://play.xfvod.pro:8088/L/L-%E9%9B%B6%E4%B9%8B%E4%BD%BF%E9%AD%94/S2/12.mp4

# 3) 拿不到公式就先猜（sha256(uri)/sha256(mediaId)/各变体）→ 全部 miss，别在这上面继续试
```

### 根因（实测，来自 Animeko 源码）

`app/shared/app-data/.../media/cache/engine/HttpMediaCacheEngine.kt`：

```kotlin
private fun httpDownloadId(media: Media, metadata: MediaCacheMetadata): DownloadId {
    val identity = listOf(media.mediaId, metadata.subjectId, metadata.episodeId)
        .joinToString("") { "${it.length}:$it" }
    val digest = Buffer().apply { writeString(identity) }.readAndDigest(DigestAlgorithm.SHA256).toHexString()
    return DownloadId("http-v2-$digest")
}
```

即 **文件名 = `http-v2-` + `sha256("<len>:<mediaId><len>:<subjectId><len>:<episodeId>")`**，输出文件 = 该 id + 扩展名（`DownloadState.relativeOutputPath = downloadId.value + mediaType.outputFileExtension`）。旧代命名是 `mediaId`（非法路径字符 `[\\/:*?"<>|]` 换成 `-`，`toSafeDownloadId`）。

**逐条核对（实测，不是推断）**：把 registry 里 23 条按上述公式算一遍，用户目录里 **9 个 `http-v2-*.mp4` 全部对上**（entries 14~22：命运石之门 / 86 / 零之使魔 / 飞跃巅峰2 / 四叶游戏 / 超电磁炮S / 四月是你的谎言 / 高分少女 / 游戏人生零）；entries 0~13 仍是旧代 `{mediaId}.mp4`，也都在场。日志里的 id↔url 10 条同样吻合。

**我们错在哪**：`AnimekoCacheLocator.engineFileCandidates()` 只拼 `media-downloads/{engine}/{mediaId}.{ext}`，`collectPathCandidates()` 又只有在条目里有 `*file*`/`*path*` 字段时才生效——而 registry 条目里根本没有路径字段。于是新命名全部落空 → `PENDING` → 集灯 missing、本地回顾不可用。

### 改动（1 个方法 + 1 个测试）

- `backend/src/main/java/com/videotagger/material/AnimekoCacheLocator.java`：`engineFileCandidates()` 现在按 **v2 优先、旧代兜底** 生成候选：`http-v2-{sha256}`、`{mediaId}`、`{mediaId 替非法字符为 -}`（只在与 mediaId 不同时才加），扩展名集合不变。
  - 长度语义：Kotlin `String.length` 与 Java 同为 UTF-16 码元数（汉字计 1），所以 `String.length()` 可直接用；`MessageDigest` + `HexFormat`（项目 Java 17）即可，无新依赖。
- `backend/src/test/java/com/videotagger/material/AnimekoCacheLocatorTest.java`：新增 `httpV2NamingHit`，用**真实三元组**（零之使魔 双月骑士 / subjectId=1103 / episodeId=2957）钉死公式，期望命中 `http-v2-73b20a95…mp4`。

## 增量二 · 银幕式「片段每次都要重新准备素材」= 帧率判定 + 无跨会话缓存（用户拍板 A+B+C2）

**用户报**：「银幕式帧速率为 24，但是大部分片段为 29.97，每次都得重新素材太麻烦了」（上一条「片段不显示」用户确认不用管）。

### 根因（实测）

**① 重编码把帧率写成 30，不是 24 —— 代码 bug**

`RecommendClipSourceService.prepare(…, timelineFps=24)` 里 `playable()` 按 24 判定，但 `export()` 根本没有 `timelineFps` 参数，`-r` 读的是**字段** `targetFps`（`videotagger.render.fps` 默认 30）：

```java
"-vsync", "cfr", "-r", String.valueOf((int) Math.round(targetFps)),   // ← 字段，不是传进来的 timelineFps
```

探针（量今天 4 个会话目录里 `media/clip-*.mp4` 的帧率）：

| 会话 | clip-193/194/199（23.98 产物） | clip-197（29.97 产物） |
|---|---|---|
| `5aa5a3ff…` | 23.98fps 直通 | 30fps / 198MB / 17:32:30 |
| `1cb11208…` | 23.98 直通 | 30fps / 198MB / 17:31:48 |
| `ab50ac12…` | 23.98 直通 | 30fps / 198MB / 17:47:48 |
| `2407d203…` | 23.98 直通 | 30fps / 198MB / 17:49:22 |

同一个会话里 23.98 的能直通（**只有 24 时间轴下才可能直通**），29.97 的却被写成 30fps —— 自相矛盾即铁证。

**② 会话目录 per-token、判定依据是源产物 → 永不收敛**

`prepare` 只查「本会话文件在不在」，缓存判定又回到源产物（29.97 恒定）→ 每次改形态/选片重建会话都从头转一遍。clip-197 在 4 个会话里各躺一份 198MB，转码时间戳与「每次重建会话」严格对应；`data/recommend-previews` 已 **113 个目录 / 2.5GB**。

**代价量化**（真机）：`libx264 -preset fast -crf 20` 实测 60s 素材 = 13s（≈4.6× 实时）；clip-197 产物 10:45 → **单次 ≈ 2.3 分钟**。

### 改动（用户拍板：A 必修 + B 必修 + **C2 取消帧率判定**）

- **A**：`export(..., double timelineFps)` 把时间轴帧率穿下去，`-r` 用它。
- **B**：新增**跨会话素材缓存** `data/recommend-clip-cache/`（`videotagger.recommend-clip-cache-dir`）：
  - 键 = `clipId + 起止 ms + videoAssetId + videoFp + 时间轴 fps`（凡影响产物字节的都进键）；
  - 命中 → 硬链优先、卷不支持硬链/跨卷则复制；未命中 → 写唯一临时名再原子改名（多标签页并发不互踩）；
  - 缓存文件永远 faststart（三条写入路径都带 `+faststart`），从缓存取的文件不用再 remux。
- **C2**：`playable()` **只看编解码**，删掉帧率那条判定 → 29.97 素材按原帧率直接进 24 时间轴。
  依据是 2026-09-20 自己实测的结论「重编码成时间轴帧率**消不掉顿挫**（靠重复帧）」——既然买不到东西，就不该付整段重编码。

### 验证证据

|---|---|---|
| 全量后端单测 | `mvn -o test` | **Tests run: 465, Failures: 0, Errors: 0** / BUILD SUCCESS |
| 相关用例 | `RecommendClipSourceServiceTest` | 6/6（原 `transcodesWhenArtifactFpsDiffersFromTimeline` **反向**成 `passesThroughArtifactWhenOnlyFpsDiffers`；新增 `reusesPreparedClipAcrossSessions`） |
