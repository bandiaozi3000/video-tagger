## 结构化场景可关闭（开场 / 序言 / 章节页 / 全片回顾 / 结尾）

### 用户要求

原话（三轮连问）：

1. 「推荐能做到假如某个片段我不想要给他单独删掉可以吗？」→ 答：片段本来就能删（三处入口），**不用改代码**。
2. 「不是片段，比如说现在有开场，序言，结尾等，这些部分能去掉吗？」→ 查现行实现，只有**序言**能靠"清空简介"去掉，其余只能缩到硬下限。
3. 「这些结构化的场景都能关闭。后续假如我新增这些结构也能做到关闭。直接在卡片上加X吧，不然后续越加越多」
   → 拍板方案：**不在右栏加一组开关**，而是**时间轴胶片条卡片上就地加 ✕**，关掉的是"这一类段"。

### 现状核查（决定实现方式的关键，实测自源码）

| 段 | 章节叙事 | 银幕式 | 改前能否关 |
|---|---|---|---|
| 开场 | `COLLECTION_OPENING` 无条件 `scene-plan.ts:188` | `SCAN`+`SETTLE` 无条件 `cinema/plan.ts:175-176` | ❌ 下限 2s |

## 增量二 · 章节式草稿不能「只重渲某块」（用户报：「当前草稿算不出段边界（非银幕式形态？」）

### 用户报的现象与提问

「不能只重渲：当前草稿算不出段边界（非银幕式形态？），无法校验，请整片重渲 什么原因」

### 根因（源码定位）

两处配合出来的：

1. `editor/rerender.ts` 的 `canRerenderChunk`：`current.length === 0` → 直接拒，文案就是用户看到的那句。
2. `editor/main.tsx` 的 `currentBoundaries`（旧版）：**第一行写死形态判断** ——
   `if (... || config.groupStyle !== 'cinema') return [];` → 章节式/片段式草稿**永远给空表**，连算都不算。

这是 2026-09-21 做「只重渲某块」时留下的限制（当时确实只有银幕式的渲染脚本输出 `boundaryFrames`）。
**但 2026-09-27 后端已经补上**（规则 §40）：`scripts/render-recommend.ts:94-99` 是
`input.style === 'cinema' ? buildCinemaPlan(...) : buildScenePlan(...)`，两种形态都输出边界；
Java 的 `RenderChunks.planByBoundaries` 通用，`VideoExportTaskService.rerenderChunk` **不做形态校验**（只查工作目录 + 块产物）。
→ **只剩编辑器这一处忘了跟着改**。

### 实现

| 位置 | 内容 |
|---|---|
| `editor/rerender.ts` | 新增纯函数 **`boundaryFramesOf(input)`**：`input.style === 'cinema' ? buildCinemaPlan : buildScenePlan` → `[0, ...scenes.map(fromFrame + durationInFrames)]`（与脚本同一套算法） |
| `editor/main.tsx` | `currentBoundaries` 改调 `boundaryFramesOf(applyLocalParams(remoteInput, config, ...))`，去掉 cinema 硬判断；注释改掉"只银幕式有"的旧说法 |

### 验证（真实数据对拍 —— 比单测更硬的那种）

用**任务工作目录里真实存在的 `data/exports/.work/<id>/render-input.json`**（任务成功/中断都留着）算出边界，
再与后端任务快照 `boundaryFrames` 走编辑器同一个 `canRerenderChunk` 比对（一次性探针，跑完已删）：


- **#9 就是修复前必然被拒的那条路**（`style=chapter` → 旧的 `groupStyle !== 'cinema'` 直接 `return []` → 报同款文案）；现在逐帧一致、放行。
- 顺带证明两侧算法同源：`buildScenePlan` 算的 127 个边界与渲染脚本当年写进快照的**完全相同**。

其余：

- `npx tsc --noEmit` 干净；`npx vitest run` → **22 files / 340 tests 全绿**（`editor/rerender.test.ts` 由 4 → 7 例：
  新增「章节式不是空表 + 两次结果稳定 + 与 `canRerenderChunk` 对得上」「片段式(clip) 也走章节计划」「银幕式走 cinema 计划」）。

## 增量三 · 「重渲第一块怎么像全片重渲」→ 跳过 probe（A）+ 进度说真话（B）

### 用户报的现象与提问

「我重新渲染第一块，为什么感觉像是全部重新渲染了？」

### 事实核查（实测，先别急着改）

**功能上只重渲了第 1 块**：任务 #9 的 work 目录里 `chunk-001..008.mp4` 的 mtime 还是 09-27 `06:55–07:23`（一个字节没动），
只有 `chunk-000.mp4` 被 `rerenderChunk` 删掉后重写。观感来自四件事：

1. **每次都要重跑 `--probe`**（`renderChunksAndConcat` 第一句）：重新 `bundle()` 整个 Remotion 工程 + `selectComposition`，
   与"渲多少帧"无关。实测上界：13:39:59 触发 → 到 13:43:11 才进入「渲染第 1/9 块」。
2. **结尾必然整片重新拼接**：`ffmpeg -f concat -c copy` 把 9 块（≈700MB）remux 成整片再覆盖成品 —— **不重编码，但整片重写**。
3. **进度/计数误导**：`mapChunkProgress` 把"第 1 块"的进度摊到全片 → 最多只到 1/9≈11%，看着像卡住；
   跳过的块 `done++; continue;` **不上报** → 面板长时间显示「已完成 0/9 块」。
4. **用户挑的恰好是最贵的一块**：原导出 42 分钟里第 1 块（3720 帧 ≈124s 画面）花了 ≈14.6 分钟，其余每块 1.5–5.5 分钟。

### 实现

**A. 分块表从任务行复原，不再跑 probe**（`VideoExportTaskService.knownPlanOf` + `RecommendVideoService.KnownPlan`）

- 数据全在行里：`boundary_frames` 的**末值就是合成总帧数**，`request_json.groupStyle` 决定 fps（`fpsOf`：银幕式 24 / 其余 30）
  → `RenderChunks.planByBoundaries(边界, 总帧, chunkFrames(fps))` 是确定性的 → **零迁移**。
- 任一项缺失/不自洽（行内 `chunks_total` 与复原块数不符）→ 返回 null → **老实回退 probe**（宁可慢一次，不能拼错片）。
- ⚠️ **坑（差点让 A 静默失效）**：库里存的是**裸 JSON 数组** `[0,1,…]`（`onBoundaries` 写的），
  而 `RenderChunks.parseBoundaryFrames` 只吃 probe 输出形态 `{"boundaryFrames":[…]}` → 直接喂会解析成空表 → 回退 probe。
  现在 `knownPlanOf` 自己包一层再解析（并保留一个裸形态兜底）。**这条是靠真实数据对拍发现的，单测里也被我写错过一次**。
- `renderChunksAndConcat` 新增 `KnownPlan` 入参；首次导出仍走 probe（没有已知表）。

**B. 进度与文案说真话**（`RecommendVideoService` + `VideoExportTaskService`）

- `pending` = 本次真正要渲的块（缺产物的）；`done` 从"已有产物"起算 → 面板显示 **8/9** 而不是 0/9。
- 块内进度按 **本次要渲的块数** 映射（局部重渲 1 块 = 0→100%，不再卡在 11%）。
- 阶段文案：`局部重渲：复用 8/9 块已有产物，本次只渲 1 块` / `渲染第 9/9 块` /
  `整片重新拼接（-c copy 不重编码，但需完整重写一次成品）`。

### 验证

## 增量四 · 「改了 JSON 重新渲染为何还不行」→ 改错了字段（`params.title`，不是顶层 `title`）

### 用户报的现象

改标题后想走"手改工作目录里的 `render-input.json` + 重渲第 1 块"这条野路子，重渲完标题还是旧的。

### 根因（实测证据）

`data/exports/.work/9/render-input.json` 里 **标题有两个位置**：

| 字段 | 用户改后 | 渲染侧读法 |
|---|---|---|
| 顶层 `"title"` | ✅ 已改成新标题 | 只在 `params.title` **为空**时当 fallback（`resolveParams(input.params, input)` 的 `fallbackText`） |
| `params.title` | ❌ **还是旧标题** | **优先**，非空即用 → `Opening.tsx:173` 的开场大标题 |

所以重渲出来的开场还是旧标题；而且这次重渲**白跑了 7 分钟**（14:32 那次 chunk-0 重渲 + 拼接，输入里唯一变化就是那个不生效的顶层字段）。

修法：把 `params.title` 也改成新标题（两个字段保持一致）→ 重渲第 1 块 → 开场标题卡换新。

**章节式里 `params.title` 只出现在 3 处**（`grep -rn "params\.title" src/`，非测试文件）：
`Opening.tsx:173`（开场大标题，用在）、`Intro.tsx:70`（序言标题，被 `prologueTitle` 顶掉）、`chrome.tsx:191`（Topbar，被 `brandTitle` 顶掉）。
→ 本例标题只落**第 1 块**，所以只重渲第 1 块不会出现"前后不一致"；换成**副标题 / 品牌名 / BGM / 主题**就不行了（Topbar 与 BGM 挂在 `RecommendComposition.tsx:40-55` 根节点，每帧都画）。

### 要记住的坑

- **手改 work 目录的 `render-input.json` 只改 `params.*`**（顶层那批只是 fallback）。这类"顶层 vs params"双份字段的坑，本质是 `resolveParams(params, fallback)` 的优先级。
- 手改 JSON 是**绕过系统**的操作：任务行、草稿、编辑器都不知情；段边界（时间轴）没变所以编辑器那道校验照样放行。临时救急可以，正式做法仍是"按当前草稿准备输入 → 只渲变化块"（见增量三的方案 A/第二步）。
- 成品**文件名**取自提交导出时的标题（`uniqueExportName(title, fmt)`），改 JSON 不会改文件名 —— 要文件名一起变就走整片导出。

### 验收中发现并修掉的两个问题（都是这个功能自己引入的）

1. **取消/中断会把 `file_path` 写成 null** → 增量更新是从**已有成品**的任务上跑的，取消一次就让那个成品在系统里"消失"（文件还在，行里没了）→ 再点增量更新被预检拦下（实测报"这个任务没有成品/工作目录"）。修：`cancel()` 与增量更新的 INTERRUPTED/ERROR 分支都**保留 `row.getFilePath()`**（首次导出时它本来就是 null，行为不变）。
2. **"影响全部块 → 整片重渲"的提示是瞬时的**：它写在 `renderIncremental` 里，毫秒后就被"渲染第 1/9 块"覆盖 → 用户根本看不到（我 2 秒轮询都抓不到）。修：把结论并进**持久**文案 —— `KnownPlan.stageLabel` 设为 `增量更新（整片重渲）` / `增量更新`，逐块文案变成 `增量更新（整片重渲）：渲染第 1/9 块`。
3. 顺带：增量更新开始时把 `progress` 也归零（原先沿用上一轮的 100%，会出现"还没渲就 100%"）。**这一条只做了代码修改与编译，未再实机复验**（复验要再跑一轮 10 分钟的重渲）。
