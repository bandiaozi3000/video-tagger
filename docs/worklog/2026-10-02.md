## 媒体筛选题材｜手动添加「常驻」（纯前端，后端零参与）

### 用户要求

2. 我给了两条路：**A** = 直接扩白名单（41 → ≥30 次命中那 112 项，需重启后端）；**B** = 前端 localStorage 常驻词 + 加删 UI。
3. 用户回「**B**」→ 开工。小改动，按项目约定**不写设计规格、不写执行计划**，想清方案直接做。

### 先验证的关键假设（不是推断，实测）

「无需后端参与」能不能成立，取决于**查询侧是否校验白名单**。读码 + 真库探针结论：

- 白名单 `MediaService.GENRES` 只出现在 `MediaMapper.listGenreCounts` 的 `IN (...)`（**只生成选项列表**）；`MediaService.genresJson()` 只是把传来的词拼成 JSON 数组，SQL 是 `JSON_OVERLAPS` —— **不校验**。
- 拿真实运行中的后端（用户 IDEA 实例，:8080）直接探：

| 词 | `GET /api/media/count?genres=<词>` | 说明 |
|---|---|---|
| （空） | 5248 | 全量 |
| 轻改 | **788** | 白名单外，查询照常命中 |
| 漫画改 | **2225** | 同上 |
| 偶像 | 218 | 白名单内，对照 |
| 厕纸 | 272 | 用户吐槽类，能查但不适合当选项 |
| 不可能存在的词xyz | **0** | → 死选项探测可用 |

- `genres_json` 的值分布（真库）：**2180 个不同值**，其中 ≥30 次命中 **112** 个，白名单只种 **41** 个 —— 说明"手动加词"真有东西可加，不是空功能。

| 位置 | 内容 |

## 媒体页筛选全维度多选（v0.32 · 用户 2026-10-02 拍板）

> 用户原话：「筛选都能多选，且都和标签一样，可勾选全部或任一匹配」→「按你的建议来，支持且和或的就有，不支持就别弄」→「不许写文档，直接编码」。
> 所以**没写执行计划**（规格文件 `docs/superpowers/specs/2026-10-02-video-tagger-v032-media-filter-multiselect-design.md` 是拍板前写的，留着当设计记录）。

### 决策（用户点头，勿复活旧方案）

| 维度 | 多选 | 且/或开关 |
|---|---|---|
| 题材 `genres` / 标签 `tagIds` / 收藏夹 `collectionId` | ✓ | ✓（**多值**，两个方向都成立） |
| 年份 `year` / 季度 `season` / 状态 `status` | ✓ | ✗ 只「任一匹配」（**单值**：`media.year`/`media.status` 是单值列；`external_work` 实测抽 200 部**每部只有 1 条**，取交恒为空集） |

- **参数名一个不改**，只把类型从标量改成 `List` → `?year=2020` 单值请求照样合法 → **Remotion 编辑器的 `CandidateFilter` 零改动**。
- **收藏夹不再是「视图路径」**：删掉媒体页里 `/api/collections/{id}/media` 分支，统一 `/api/media?collectionId=a,b`（两条路径的列与 `ORDER BY a.id` 一致，结果等价）。收藏夹视图自己的 `collFilter` 与 `/api/collections/{id}/media` 端点**没动**。
- 顺手删掉 `MediaService.genresJson()`（手拼 JSON + 手写转义），改 `JSON_ARRAY(<foreach>)`（OR）/ `JSON_CONTAINS(genres_json, JSON_QUOTE(?))`（AND）。

### 改动面

- 后端：`MediaMapper`（新增 `STATUS_FILTER`/`YEAR_FILTER`/`COLLECTION_FILTER`，`SEASON_FILTER`/`GENRE_FILTER` 改写，6 个方法签名全改）+ `MediaService`（4 个入口 + 删 `genresJson`）+ `MediaController`（4 个端点 + `genreMode`/`collectionMode`）+ `CollectionService`（标量包成单元素列表喂共用片段）。
- 前端 `app.js`：`mediaFilter` 单值维度改数组、`tagMode` 收进 `mediaFilter.mode = {genres,tagIds,collectionId}`；`dimIsMulti()` 退役 → 新增 `DIM_MODE_CAPABLE`/`isModeDim()`；取值列表不再塞「全部（不限）」（清空走 chips 的 ×）；且/或开关从「只给标签」泛化到多值维度；`buildMediaUrls` 数组 join + 删收藏夹路径分支。

### 三个真踩的坑

1. **MyBatis `@Param` 顺序陷阱（本次最阴）**：`countFiltered` 的签名里 `genreMode/collectionMode` 与 `q` 的相对位置和 `MediaService` 的位置实参错位 → **不报错、不抛异常，只是默默数出 0**。是新增 IT 里「count 必须等于 list 条数」那句断言抓到的。教训：位置参数型的 mapper 调用，要用「同参同条件两处结果对拍」钉住，别指望编译期。
2. **`mvn -o test-compile` 不会重编测试**：改完 main 的方法签名后它输出 `Nothing to compile - all classes are up to date` + **BUILD SUCCESS**，旧 `.class` 仍在（`javap` 能看到的还是 17 参的旧描述符）。根因：增量编译只看 `.java` vs `.class` 时间戳，全 null 实参的旧调用不会被判定为受影响。做法：`rm -rf target/test-classes` 再 test-compile（**别用 `clean`**，用户在跑 IDEA 实例）。
3. **静态资源版本戳**：`index.html` 的 `app.js?v=` / `app.css?v=` 手动 bump 到 `20261002-filter-multi1`，否则浏览器吃缓存看不到改动。

### 「筛选萝莉且日常，萝莉只有 300 多部，为何筛出 1000 多部」——根因：前后端版本不一致（2026-10-02）

**先验数据（实测）**：
```
题材「萝莉」 310 部 ｜ 题材「日常」 1750 部 ｜ 萝莉 AND 日常 = 196 部 ｜ 萝莉 OR 日常 = 1864 部
标签表里只有 3 个词条（性转 / 趣味拉满 / 萝莉[0 引用]）→「日常」根本不是标签
```
→ 这两个词是**题材**，用户单选 1 个时看到 310（对得上"300 多"），选了 2 个却得 1000 多 = **OR 的结果（1864）**。

**根因链（三条证据）**：
1. 接口实测：`genreMode=AND` 与 `genreMode=OR` **返回同一个数（1864）** → 参数被当空气。
2. 代码读证：`MediaMapper.GENRE_FILTER` **有** AND 分支（`JSON_CONTAINS + JSON_QUOTE`），`MediaFilterMultiIT` 也断言了 AND=交集 → **代码是对的**。
3. 后端日志原话：`MethodArgumentTypeMismatchException: ... to required type 'java.lang.Long'; For input string: "17,4"` → **跑着的实例仍是旧代码**（`collectionId` 还是单个 `Long`），所以 v0.32 新加的 `genreMode/collectionMode/多值参数` 全被忽略 → 题材**永远 OR**。

**结论**：前端已升到 v0.32（`app.js?v=…tag-v034` 会发 `genreMode`），后端没重启 → **静默忽略新参数、给出错结果**。**重启后端即修复**（预期「萝莉 且 日常」= 196 部）。

**暴露的真问题（值得单独修）**：**前后端契约不匹配时不报错，只静默给错结果**。这类"静默错"今天第二次出现（第一次是静态资源版本戳）。建议加**契约版本自检**：后端暴露 `apiVersion`，前端加载时对不上就横幅提示「后端需要重启」。

### 「标签池新增标签未生效」根因 = 通用确认弹窗点「确定」也跑 onCancel（用户 2026-10-02）

**先排除后端**（curl 自清理：建词条 → 关联媒体 2130 → 查使用位置 → 反关联 → 删词条）：
```
① POST /api/tags {"name":"探针临时词条ZZ"} → {"id":416,...,"refCount":0}
② POST /api/media/2130/tags {"tagIds":[416]} → 200
③ GET /api/tags/usage?tagId=416 → {"total":1,"media":[{"id":2130,...}]}   ← 立刻生效
④ DELETE /api/media/2130/tags/416 → 200    ⑤ DELETE /api/tags/416 → 204
```
后端没问题。浏览器探针（写请求**全部拦成假成功**，不碰真库）分两条路：
```
【已存在词条 趣味拉满】POST /api/media/11355/tags {"tagIds":[407]}   ← 正常
【全新词条 探针临时新词QQ】弹确认层[取消|新建并打上] → 点「新建并打上」后：
    只发了 GET /api/tags?prefix=…，**POST /api/tags 根本没发**，输入框还留着字
```

**根因**（`static/app.js`）：
```js
document.getElementById('confirm-modal-ok') → const fn = confirmModalAction; closeConfirmModal(); if (fn) fn();
function closeConfirmModal() { …; if (cancel) cancel(); }   // ← 无条件跑 onCancel
```
点「确定」时先跑 `onCancel` → `confirmAsync` 的 promise 以 **false** 结束 → `if (!ok) return null` → 整条新建+打标链路被中止。

**这行来自 `6fca026`（v0.24.2「全站弹窗统一」），是老 bug**，不是今天引入。同族的 `promptModal` 没这个问题（它的 `closePromptModal` 不回调 onCancel）。

**修**：`closeConfirmModal(cancelled = true)`，只有取消路径才跑 onCancel；OK 处改 `closeConfirmModal(false)`。注意 OK 处理里 `const fn = confirmModalAction` 仍在 close 之前取 ✓。

**修复后实测（同一探针）**：
```
【全新词条】POST /api/tags {"name":"探针临时新词QQ"} →FAKE 200
           POST /api/media/11355/tags {"tagIds":[99999]} →FAKE 200
           refreshMediaDetail 的 GET 一串；输入框清空；客户端词池 9→10
events=[]
```
**同根因的第二个受害者（推断，未单独跑那条链路）**：`app.js:4924` 导出前「仍有 N 段未准备 → 导出可用版？」那个 `confirmAsync` —— 以前点「导出可用版」也会被当成取消。
**受影响的非 Promise 调用只有一处**（BT 缺源集确认，`app.js:7451`）：它以前点「确定」时会先被 onCancel 把状态改成「已取消」，现在不会了 ✓。

### 「跳转后没返回」→ 系统性补返回入口（用户选 A + 要求扫全）（2026-10-02）

**扫全网的结论：跳转没返回的共 4 处**（不只我动过的那 2 处）：

| # | 跳转 | 改前 | 改后 |
|---|---|---|---|
| 1 | 标签页 →「去媒体页筛选」→ 媒体页 | `showView('media')` 不进栈 → **无返回** | `pushView('media')` + 媒体页「← 返回」 |
| 2 | 标签页 → 点媒体条目 → 媒体详情 | 有按钮但文案写「← 返回媒体」（实际回标签页）**在撒谎** | 文案按栈顶来源动态（实测「← 返回标签页」） |
| 3 | 媒体详情 →「📋 在标签页查看」→ 标签页（带作用域） | `showView('tags')` 不进栈 → **无返回** | `pushView('tags')` + 标签页「← 返回」 |

**实现要点**
- 新增 `syncBackButtons()`（`showView()` 末尾调用）：三个新按钮（`#media-back`/`#tag-back`/`#search-back`，复用现成 `.back-btn` 样式）**只在 `viewHistory.length > 0` 时出现** —— 从侧栏直接导航进来不摆废按钮。

- **侧栏导航清栈**（`viewHistory.length = 0`）：否则会留一个指向"已被离开的流程"的幽灵返回。
- 时间线：拆出 `loadTimeline(v)`（不入栈）供 `goBack` 复用；删掉 `fromMediaDetail`/`fromEpisodeDetail` 两个全局布尔（4 处赋值 + 声明 + 那个手写 handler 全清）。
- 标签页也纳入 `SCROLL_RESTORE_VIEWS`（返回时恢复滚动位置；展开的哪一行本来就靠 `tagExpandedId` 保留）。
