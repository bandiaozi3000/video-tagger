## 增量一 · 候选库「某年只显示 5 部，与收藏夹数量不符，强刷就好」

**用户报错原文**：「推荐候选为什么只显示5部，与收藏夹数量不符。强刷一下就又好了，排查原因」（附截图：候选 554 部 · 筛选中 1，`2019 → 28 部`、红框 `2018 → 5 部`、`2017 → 1 部`）。
用户回复「一起做」= 采纳 (A) 拼页校验 + (B) 表头如实；随后的「可以」= 再加 (C) 失败时给「重载候选库」按钮。

### 一、结论（一句话）

不是"只加载 5 部"，是**那一会话里拼进列表的页不是同一份一致数据**，而前端 `[...current, ...items.filter(不重复)]`
把重复行**静默丢掉** → 列表永远少几部、年份段错位；错掉的那份列表**没有重试入口**，所以只有整页重载（强刷）能恢复。

### 二、排查（可复现的探针与命令）

1. **看现状**：候选库总数与"媒体页/收藏夹"同源，先确认目标年份真值。

   ```bash
   curl -s "http://localhost:8080/api/media/count?collectionId=13"                 # 554（当时）→ 553（半小时后）
   curl -s "http://localhost:8080/api/media/count?collectionId=13&year=2018"        # 20  ← 截图里只有 5
   ```

2. **走前端真实请求序列**（`limit=30`、`offset=0…540`、`collectionId=13&sort=year&order=desc`），统计行数/唯一数/年份段：

   ```
   p1…p18 = 每页 30 行；p19 = 14 行 → 共 554 行，唯一 554，重复 0，年份单调不增，各年计数与 count 接口一致
   ```

   → **当前后端是干净的**（排序全序兜底 `ORDER BY (a.year IS NULL), a.year DESC, a.id DESC`，0e3529c / 今天 05:52 提交，
   JVM 今天 11:55 重启后已生效）。

3. **用"去掉 `, a.id` 的旧 SQL"复现旧行为**（`docker exec vt-mysql mysql`，19 页 × 30）：

   | 版本 | 取回行 | 唯一 | 说明 |
   |---|---|---|---|
   | `ORDER BY (a.year IS NULL), a.year DESC`（旧） | 553 | **453** | 少 100 行（重复行被前端丢掉） |
   | `… , a.id DESC`（现） | 553 | **553** | 0 重复 |

   旧 SQL 前 5 页唯一数 = **116**，与 `docs/worklog/2026-09-25.md §增量十一` 记录的数字一致；按前端去重逻辑复算
   「2026 异世界」= **57**，与用户昨天报的「87 部只加载 57 部」**完全对上** → 旧行为已复现。

4. **逐页复算旧 SQL 的年份段**：同一滚动深度给的是 `2019×28 | 2018×**6**`，再下一页 `2018×20 | 2017×16`。

### 三、根因（分三层，实测 / 推断分开）

| 层 | 内容 | 状态 |
|---|---|---|
| ① 后端 | `sort=year` 排序不是全序 → MySQL 翻页重复/跳行 → 前端去重后少行 | **实测**（上表），**已修**（§25 同一根因的第二次） |
| ② 前端 | 拼页**静默去重**：重复/漏行不报错、失败页不重试、页码照样前进 → 错列表无法自愈 | **实测**（读码 `panes.tsx:1192/1194`），**本次修** |
| ③ 数据 | 会话期间集合归属会被改写：查的半小时里「异世界」554 → 553、2004 年 2 → 1（media 总数 5249 不变，不是删档） | **实测**（`/api/media/count` 前后对比），**无法预防**（只能靠②校验兜住） |

**推断（未验证）**：截图那一处 `2019×28` 紧接着 `2018×5` 紧接着 `2017×1` 在数学上**不可能**由「按年份排序的分页」产生 ——
年份降序下既然 2019 的 28 部齐了、又出现了 2017 的行，2018 的 20 部必须全在前面（我逐页复算旧 SQL 同深度是 **6**）。
所以那一次会话里除了①之外，中途还掺进了**不同源/不一致的一页**（漏页或集合改写），才会是 5。
另：截图里 `2017 1 部` 没带「已加载」前缀 → 当时 `hasMore` 已为 false（列表自认加载完了），与"只是没滚到底"矛盾，
进一步指向列表被拼杂。**这一处只有推断，没有抓包证据**（那时的网络请求已经没了）。

## 增量二 · 序言/简介支持「分段 + 加粗 + 重点色」（最小富文本，用户选 A）

**用户诉求原文**：「这个序言简介用富文本框实现好做吗？我希望有层次段落以及重点突出等要素」→ 听完三档方案后回：「A。最小简单实现，能分段，加粗，颜色标记等就可以」。

### 一、判断（先说结论）

不接富文本编辑器。`config.intro` **保持纯字符串** —— 它要过**草稿 / 模板 / 导出任务**三层 JSON payload，
换 HTML 就要消毒 + 换数据模型；而且这一屏排版预算紧（按字数自动收字号 + 每段行数收口），
**右栏 1920×1080 Player 本来就是所见即所得**，缺的只是"插入方便"。所以：标记留在纯文本，解析只发生在渲染侧。

### 二、语法（唯一真源 `backend/remotion/src/rich-text.tsx`）

| 写法 | 效果 |
|---|---|
| 空行 `\n\n` | 分段（段间距 `size * 1.0` ≈ 原来一个空行） |
| 段内 `\n` | 段内换行（沿用 `white-space: pre-line`） |
| `**文字**` | 加粗（**同时提亮**，见下） |
| `==文字==` | 重点色（chapter 用 `theme.colors.gold`，银幕式用该场景 accent）+ 加粗 |

未闭合标记 / `****` **当普通文字**，不抛错、不吞字。旧纯文本**零迁移**（用户草稿里那 55 字原文现在渲染效果基本不变）。

## 增量三 · 序言简介升级成「语义富文本 + 预算条」（用户：「都改，颜色做个区分，红色是提醒的」）

### 一、取舍口径（留语义、砍排版）

这屏是**朗读节奏 + 画幅预算**驱动的画面，所以功能只由这两条推导：

- 留：**这是标题 / 这是条目 / 这段要突出**（突出带语义，不是让用户挑颜色）
- 砍：字号、字体、对齐、缩进、表格、图片、链接、**颜色自选器** —— 排版归模板；放开排版就守不住上面两个约束
- 明确不接真富文本（contentEditable/TipTap）：与上面这批功能完全重叠，代价是 payload 换 HTML（要消毒）+ 迁移 + 100~250KB 依赖 + 行数/字号收口重算

### 二、落地能力

| 能力 | 说明 |
|---|---|
| 块级三档 | 空行分段 ｜ `## 小标题`（1.3× + 金色 + 行高 1.4）｜ `- 条目`（金色圆点 + 悬挂缩进；**相邻条目**间距 0.25 字号成组） |
| 行内四标记 | `**加粗**`（同时提亮）｜`==重点==` 金 ｜`!!提醒!!` 红 ｜`++信息++` 青 —— **语义固定**，不随媒体/章节轮转 |
| 编辑器 | 6 个按钮（小标题/条目/加粗/重点/提醒/信息；块级按钮再点一次＝取消）+ 语法 hint + **预算条** |
| 预算条 | `23 字 · 1 块 · 约 4 行 / 上限 8 行 · 字号 100%`；超时长的**橙字**提示「5 秒 ≈ 易读 25 字」；连下限都放不下 → **红字**「内容过长，成片会被裁切」 |
| 自动收字号 | 旧的「>120 / >220 拍两档」换成 **`fitIntroSize` 二分**（按 `INTRO_LAYOUT` 预算，下限 0.72×），渲染与预算条**同一份常量/算法** |
| 银幕式 | 那行简介取**第一块**（clamp 1 不变），并按场景提示「只显示第一块」 |

### 四、⚠️ 事故与恢复（不粉饰）

**我把用户手写的简介清空过一次。** 过程：浏览器验收脚本在**草稿还没加载完**时采样 textarea（拿到空值），

**实测**（读码 + 数据流，未做真实素材变更复现）：

| 层 | 事实 |
|---|---|
| 会话目录 | 片段素材落在会话目录 `media/clip-<clipId>.mp4`（`RecommendClipSourceService.prepare`） |
| 关键判断 | `if (!Files.isRegularFile(output)) { prepareOne(...) }` —— **文件已存在就直接复用**，只看文件名，不看素材本体 |
| 后果 | ① 库里把某片段**重新物化**（换了产物/区间）后，同一会话里旧 `clip-<id>.mp4` 照旧被用 → 预览不变；② 片段 `timestamp/end` 改动同理（文件名里没有区间） |
| 为什么「强刷/新会话」就好 | 新 token = 新目录 = 重新 `prepareOne`（也因为这样，用户会觉得"时好时坏"） |
| 为什么指纹（自动检测 B）也救不了 | `metaFingerprint` 只覆盖展示字段（标题/年份/格式/分类/来源/封面链/简介/标签/集数），**不含片段素材身份** → 素材变了指纹不变 → 连重建都不会触发 |

**可复现探针**（无需改库，看会话目录即可）：

```bash

ls -l data/clips/ 2>/dev/null || true                        # 与库里物化产物比 mtime
```

**建议修法（待用户点头）**：把会话产物文件名改成**内容寻址**——`clip-<id>-<hash8>.mp4`，hash 取 `clipId | 源产物路径+mtime | startSec | endSec | 目标 fps`；素材或区间一变就是新文件，手动「重新读取素材」立刻生效（旧文件同片段前缀顺带清理，删不掉就留着等会话回收）。改动集中在 `RecommendClipSourceService`（约 15 行）+ 一条单测；需要重启后端 + **真实素材变更**才能端到端验收。

### 二、顺手修的两个既有毛病（都先定位到证据再改）

**1）候选网格的年份段会残留幽灵节点（改成平铺 + 唯一 key）**

- 症状（探针可复现）：`只看已选` 拉到 196 部 → `📅 按年份` 开 → 关，之后 grid 里 **state 是 196 张、DOM 却是 206 张卡 + 6~45 个旧年份段**，DOM 永远对不上 state；此时切「年份 ↑」，列表其实已按 asc 取回（`n=30 年份 2000→2012`），但读到的仍是旧那些卡 → 验收项假红。
- 根因：年份段用 `<React.Fragment key={年份}>` 包一层，里面又混着无 key 的组头与按媒体 id 作 key 的卡片；同一年在**列表还没换成年份序的瞬态**里会拆成多个连续段 → 重复 key，React 复用/丢弃时把上一版的一截节点留在 grid 里（本库真有 1887/2002/2018/2061 这类 id，跟年份数字同域）。
  - **实测**：state 与 DOM 数量对不上（`list=196` vs `grid 里 206 张卡 + 6~45 个旧段`）；关分组后 DOM 子节点 212（应 196）。
  - **推断**（未拿到直接证据）：机制是重复 key；整轮跑下来控制台**没有** React 的重复 key 警告，所以「为什么 React 会留下节点」这层只到“现象确定、机制存疑”。

## 增量七 · 用户报「重新拉取这块封面依旧没变」——Bangumi 外部封面缓存**命中即返回**，来源 URL 变了也不知道

### 一、结论（一句话）

编辑器/成片的封面读的是**本地缓存** `covers/ext/{mediaId}.{ext}`（第一次下载后永不回查），
而媒体页读的是**远端 `external_cover_url` 直出** → 库里换了封面，媒体页新、视频里旧；
「重新读取素材」只是把同一张旧图再给一遍，跟它无关。

### 二、排查（可复现的探针与命令）

```bash
# 1) 库里这部的封面链：没有本地封面，只有 Bangumi 远端 URL
curl -s "http://localhost:8080/api/media?q=犬夜叉&limit=2" | node -e '...'   # cover_path=null, external_cover_url=.../2784_DiZ0d.jpg
# 2) 缓存文件比 external_work 行旧
ls -l --time-style='+%m-%d %H:%M' data/covers/ext/7427.jpg                    # 09-26 04:28
docker exec vt-mysql mysql -uroot -proot123456 -D video_tagger \
  -e "select cover_url, from_unixtime(updated_at/1000) from external_work where media_id=7427;"   # updated_at = 09-26 14:45
# 3) 渲染输入里给编辑器的是什么
curl -s -X POST http://localhost:8080/api/recommend/session -H "Content-Type: application/json" \
  -d '{"ids":[7427],"perScreen":1}' | node -e '...'   # coverAssetPath = "/covers/ext/7427.jpg" ← 04:28 那张
```

代码三处一对就清楚：`CoverService.ensureExternalCover`（命中即 return）→ `RecommendService:280`（视频用缓存）→ `static/app.js:2130`（媒体页用远端）。

### 三、根因

`ensureExternalCover` 的文件名只绑 `mediaId`，命中缓存后**从不比对来源 URL**；缓存与来源之间没有任何时效/版本关系 → 来源变了也不知道。
（用户在本轮确认：媒体页显示的是新封面，视频里是旧的 —— 与推断一致。）

### 四、改动前后对比

| 项 | 之前 | 现在 |
|---|---|---|
| 缓存文件名 | `covers/ext/{mediaId}.{ext}` | `covers/ext/{mediaId}-{urlHash8}.{ext}`（`externalCoverKey`：URL 的 SHA-256 前 8 位） |
| 来源 URL 变化 | 无感（永远吃第一张） | 新文件 → 立刻换新；写入后清掉同 mediaId 的旧文件（含老命名） |
| 老缓存文件 | 命中即用 | **作废**（来源未知，不能当"当前 URL 的图"）；重启后用到的那几张会重下一次，其余可手动清 |

- ⚠️ **端到端未验**：新类是 Java 侧改动，运行中的实例（14:48 启动）还是旧 class → 要用户**重启后端**后才能看到
  `coverAssetPath` 变成 `ext/7427-xxxxxxxx.jpg`（重启后我可以立刻用上面的 session 探针复查）。

### 六、遗留 / 待用户决定

1. 老命名缓存文件（`data/covers/ext/*.jpg`，约 226 张）已成死重量：**建议重启后按需重下**，想清干净自己删即可（纯缓存，真源是 `external_work.cover_url`）。

## 增量十三 · 修「音乐条显示的是视频进度」（2026-09-26 用户报）

**用户反馈**：「音乐条进度显示有问题，显示的是视频进度」。

### 一、根因（三处，都在 `chrome.tsx` 的 `BgmBadge`）

| 元素 | 旧口径（错） | 现在 |
|---|---|---|
| 进度条 | `(帧 − 窗口起点) ÷ 窗口长度` | **曲内位置 ÷ 曲长** |
| 左边时间 | **绝对视频时间**（窗口起点 + 比例×窗口） | 曲内位置（循环后归零） |
| 右边时间 | **窗口长度**（曲长探不到时就是**全片时长**） | **曲长** |

`bgmRange=all` + 曲长探不到（ffprobe 失败 → `durationSec` 缺省）时，时间轴退化成「一首盖满全片」→ 三处数字必然等于视频进度。真草稿实测（839.5s 片长 / 200s 曲子）：修前 `1:00 / 13:59`，修后 `1:00 / 3:20`。

### 二、顺手查出的两个同族问题（都改了）

1. **`<Audio startFrom>` 单位是帧、不是秒**（Remotion 类型定义写明 "in frames"；`getExpectedMediaFrameUncorrected` 按帧插值）。旧代码直接传 `startFromSec` → 结尾「曲子后半段」实际只跳到**第 3.7 秒**（112 被当成第 112 帧）。现在统一走 `bgmStartFromFrames(slot, fps)`。**这会改变你听到的结尾 BGM**（真的从后半段起放）。
2. **静音段挂着一条假音乐条**：旧代码找不到活动曲时回退第 0 条/最后一条 → 「BGM 只在开头+结尾」的片子中间十几分钟也有条，写着无意义位置（实测 300s 显示 `1:25 ↻`）。新增 `bgmSlotIndexAt()`（按该条自己的尾巴判定）→ 无音乐不渲染条。
