#### 二、根因（两个都在代码里）

**问题一**：`ClipService.ensureEpisode` 集匹配**只认 `episode.video_fp`（URL 指纹）**，指纹没命中就无脑新建。
而 `TitleParser` 明明已经解析出 `episodeNo=5`，这个集号**完全没参与匹配**；`EpisodeMapper.selectByMediaEntryAndEpisodeNo` 早就写好却**无人调用**。
→ 这不是轻音专有：**任何 Bangumi 同步过的番，第一次用扩展打标签都会建重复集**。

**问题二**：三处标签池对比（`app.js`）——

| 位置 | 函数 | 能否新增 |
|---|---|---|
| 媒体详情 | 标签池 +「🏷 标签(n)」批量打标 | ✅ |
| 集详情 | `renderEpisodeDetailTags` 末尾挂 `+ 添加集标签` | ✅ |
| **片段详情** | `renderClipTags` **只画 chip，什么都没挂** | ❌ |

唯一入口是「片段详情 → 编辑」弹窗那一行「标签」，且老代码注释写明**多标签只编辑第一个** —— 一改就只剩 1 个标签（`PUT /api/clips/{id}` 是 `tagIds` 全量替换）。

#### 五、遗留风险 / 待用户决定

- **同一集换来源 URL 仍会新建集**：指纹被第一个 URL 占掉后，第二个来源的 URL 走不到认领分支。当前只保证「同 URL 重复打标不重复建集」，跨站同集去重不在本次范围。
- **集号口径不一致时会认错集**：兜底只按 `media_id + episode_no`，若站点标题的集号与 Bangumi 集号不同口径（例如把特别篇算作第1集），会认领到错误的那一集。缓解手段只有「只认领无 URL 的集」，没有更强校验。
- **认领是写操作**：`ensureEpisode` 现在会 `updateById` 已有集（回填 url/指纹）。若将来集有并发写入场景，需要考虑竞争（当前单用户，未处理）。
- **待用户重启后端**（8080 是 IDEA debug 实例，Java 改动不生效）后**重新用扩展打一次第5集**，用真实链路验收；静态资源部分刷新页面即可。
