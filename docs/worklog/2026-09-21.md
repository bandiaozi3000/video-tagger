## 增量二：分块渲染 / 暂停 / 断点续渲（"一次性执行完"）

### Spike 先行（规格 §11 要求：不通过就不写实现）

第一次 spike（`renderMedia` 分两块 + `ffmpeg -f concat -c copy`）**抓到两个坑**：

1. **音轨会整段丢** ✗ —— `c0`（开场段，本身没有音频内容）里连音轨都没有，
   而 concat 按流索引对齐 → 拼接产物**没有音频流**。
   修法：`enforceAudioTrack: true`（让每块都带一条（可能是静音的）音轨）。
2. **接缝有 0.18s 空洞** ✗ —— 逐帧时间戳实测：块 0 结束在 `5.966667s`，块 1 却从 **`6.144`** 起。
   拼接后画面对不上（PSNR **23.5dB** ✗）。
   修法：concat 清单里每个 `file` 后面写 `duration <秒>` → 接缝变成 `5.9667 → 6.0000` 连续 ✓。

**修完复测（通过）**：

| 指标 | 结果 |
|---|---|
| 接缝时间戳 | `5.933333 → 5.966667 → 6.000000(I)` 连续 ✓ |
| 拼接 vs 单次整段 PSNR | **53.6 dB**（视觉无损；min 43.5 在接缝）✓ |
| 音频帧数 | `288 + 285 = 573` **精确相加** ✓（无缝）✓ |
| 各块单独 vs 整段 | 62.4 dB / 50.9 dB ✓（说明块本身没渲错，问题只在拼接）|

## 增量三：切点按时间轴段边界对齐（用户："能做到按时间轴那种分块去渲染吗" → "按这个做"）

### 为什么不能纯按段切

段长度极不均匀：片名卡 5s，而片段 **3s ~ 9 分 21 秒**（真实草稿里 #189 那段 = **560.9s**）✗
→ 纯按段切会出现"一块 9 分钟"：暂停要等 9 分钟、块粒度失控 ✗。

### 做法（两步纯计算）

1. **探边界**：渲染脚本 `--probe` 除了总帧数，还用**同一份 plan**（`buildCinemaPlan`；同输入 → 时长确定，`seed` 只影响摆位不影响时长）打印 `boundaryFrames`，
   并**校验** plan 与 composition 的总帧数是否一致（不一致打 warn）；
2. **Java 贪心切**（`RenderChunks.planByBoundaries`）：
   - 先把每段切成 ≤ target 的**原子片**（超长段在段内按 target 细分）；
   - 再**贪心合并**相邻原子片，累计 ≥ target 才切一刀；
   - 保证**不重不漏**（各块相加 = 总帧数、块与块首尾相接）。

拿不到边界（非银幕式模板 / 探帧失败）→ **自动回退固定 2 分钟切法**（后向兼容）。

### 实测 / 演示

- 探帧真实输出：`{"composition":true,"durationInFrames":1173,"fps":30,...,"boundaryFrames":[0,165,300,360,513,573,813,873,1023,1173]}` ✓
- 手算演示（POC 边界 + target 300 帧）：`[0,299]` / `[300,812]` / `[813,1172]` —— 切点 **300 / 813 全在段边界** ✓
- `RenderChunksTest` 扩到 **8 条**（+4：切点必落在边界且首尾相接且总数不变 / 超长段段内细分且块长不爆 / 无边界回退 / 退化输入去重裁剪）✓

`mvn -o test -Dtest=RenderChunksTest` → **8 passed** ✓ · 编译干净 ✓
（容器 IT 仍受 Docker 故障影响，见增量一）

### 顺带回答了用户的技术提问

"Remotion 为什么比 Premiere 渲染慢这么多" —— 已沉淀进 `docs/learn/technology.md`（同一天条目）：

- Remotion 每帧 = **在无头 Chrome 里完整跑一遍网页渲染**（React diff + CSS 布局 + 合成），
  带视频的帧还要 **ffmpeg 抽源视频那一帧**；Premiere 是原生 GPU 管线（解码→特效→编码，像素只走固定硬件路径）；
- 实测吞吐：720p **650 帧/分**、1080p **380 帧/分**、4K **108~125 帧/分** → 24fps 片子，1080p ≈ **4 倍实时**、4K ≈ **13 倍实时**；
- 我们换到的是**可编程性**（24 部片单/掠影/滚动封面墙/逐帧动画都是代码）；
- 真要提速的优先级（都实测过）：**降分辨率（4K→1080p 快 3.5×）** > 去掉片段模糊背景视频（片段帧快 35%，16:9 素材零画质代价）> 并发（只 7~13%）> 编码参数。

## 增量四：预览 vs 导出 —— 用探针把「预览快、导出慢」钉死（用户：为何预览那么快导出那么慢）

### 用户的反驳（对的）

> 预览我能直接一秒一秒看完，那实时渲染的速度不应该和我预览完的速度一样吗？

我上一条拿"预览只渲你看过的一段"当理由是**站不住的**（用户确实全看了）→ **撤回**。改用实测。

### 探针（新增，可复用）

`backend/remotion/probe/fps-probe.tsx` + `run-fps-probe.ts`（照既有 probe 骨架：vite 构建 → 本地静态服务 → puppeteer 开系统 Chrome → 播放 → 读计数）
`npm run probe:fps`（无头）/ `PROBE_HEADED=1 npm run probe:fps`（开窗口自己看）
`PROBE_WIDTH/PROBE_HEIGHT/PROBE_SECONDS` 可换分辨率与时长。

三个计数器（都在页面主线程）：**raf**（真能画的帧率）、**合成渲染/s**、**Player 光标/s**（只说明时钟在走）。

### 实测（无头 Chrome，本机 16 核）

| 分辨率 | 预览 raf | 预览光标 | 预览覆盖度 | 导出实测 | 差距 |
|---|---|---|---|---|---|
| 1280×720 | 52/s | **29.7/s** | **99%** | 92 ms/帧 = 10.9 fps | 预览 **2.7×** |
| 1920×1080 | 57/s | **29.4/s** | **98%** | 158 ms/帧 = 6.3 fps | 预览 **4.7×** |
| 3840×2160 | 58/s | **27.6/s** | **92%** | 555 ms/帧 = 1.8 fps | 预览 **15×** ✗ |

**结论：预览真的接近满帧（4K 下 92%），所以"预览流畅"不是丢帧假象** —— 而是**同一逻辑工作的两套物理实现**差了一个数量级。

### 归因（关键：像素数）

预览把 3840×2160 的合成 **CSS 缩放到面板尺寸**再显示 → Chromium **按缩放后的尺寸光栅化**（约 1280×720 量级）
→ 光栅像素数只有导出的 **1/9**（(3840×2160)/(1280×720) = 9）→ 与实测 15× 的差距基本吻合 ✓
叠加上：浏览器合成走 **GPU**、`<video>` 顺序**硬件解码**、**不编码**、跨帧**复用**；导出则是无头**软件光栅满像素** + **逐帧 ffmpeg 抽帧** + **每帧截图过 DevTools 协议** + **x264 编码**。

### 可迁移规律

1. **"预览流畅"不能用来估导出时间** —— 预览的光栅化像素数 ≈ 显示尺寸，导出 ≈ 合成分辨率；两者可以差一个数量级。
   估时间只能看进度面板的 ETA（那是真值）。
2. **像素数是第一成本**：导出 4K→1080p 实测快 3.5×，与"像素数比例"同向；预览/导出的 15× 差距也主要是像素数差。
3. **排查"为什么慢"时先分清"时钟在走"和"画面画出来了"** —— Player 的 `getCurrentFrame()` 只是时钟；
   要测"真能画"的上限得数 `requestAnimationFrame`（主线程忙时浏览器会跳过它）。

### 未验证

- 探针跑在**无头 Chrome**（rAF 由虚拟帧源驱动，不等同于有头窗口的 vsync 上限）；要复验可 `PROBE_HEADED=1 npm run probe:fps`。
- "光栅化按显示尺寸"是**推断**（Chromium 合成器行为），本项目未直接观测像素数；但 1/9 与 15× 的吻合度支持它。

**⚠️ 勘误（同日晚，自己做的实验推翻了本条的结论）**：

为了验证"预览便宜是因为按显示尺寸光栅化"，把探针视口开到 **3840×2160（1:1 显示 4K 合成）** 再测：

| 实验 | 4K 合成 + 1280 视口 | 4K 合成 + **3840 视口（1:1）** |
|---|---|---|
| 预览光标 | 28.1 fps（94%） | **29.9 fps（100%）—— 没掉** ✗ |

→ **"按显示尺寸光栅化"的解释不成立** ✗（至少不是主因）。
更可能的真相（推断）：探针跑在**无头 Chrome**，而无头很可能**根本不做真实光栅/绘制** ——
旁证是两次 raf 都稳在 **58~59/s、零长任务**（真在画 4K 模糊视频层时主线程不可能这么闲）。
→ 所以"预览满帧"**很可能是无头环境的产物**，本条的结论**降级为存疑**。

**决定性复验**：`PROBE_HEADED=1 npm run probe:fps`（有头浏览器跑同一探针）。
已同步修正 `docs/learn/technology.md` 里的对应小节。

## 增量五：把「导出慢」拆开 + 找到唯一有效改进（用户：测试，找出真实差距，看看能不能改进）

### 拆解方法（不用新仪器）

`onProgress` 回调里 **`frames` 先涨满、`encoded` 后涨满** → 用时间戳把一次渲染切成
**「帧生产阶段（合成+截图+抽帧）」** 与 **「编码阶段（x264）」** 两段 ✓。

### 实测（同一时段同一环境，1080P 片段幕 240 帧，1080P 卡片幕，c=2）

| 配置 | 总 ms/帧 | 帧生产 | 编码 | 相对基线 |
|---|---|---|---|---|
| 片段-**基线** | **121** | 110 | 11 | — |
| 片段-`offthreadVideoThreads=4` | 122 | 109 | 12 | +1% ✗ |
| 片段-`offthreadVideoCacheSizeInBytes=1G` | 123 | 106 | 17 | +2% ✗ |
| 片段-`jpegQuality=60` | 124 | 109 | 14 | +2% ✗（体积反而更大） |
| 片段-`x264Preset=superfast` + `crf=20` | 121 | 107 | 15 | **+0% ✗** |
| 片段-全家桶组合 | 123 | 109 | 14 | +2% ✗ |
| **片名卡-基线（无视频层）** | **70** | **51** | 18 | **−42%** ✓✓ |

### 三条硬结论

1. **编码不是瓶颈**（11~18 ms/帧 ≈ 10%）→ 调 `crf`/`preset` 白费 ✓
2. **`offthreadVideo*` 与 `jpegQuality` 全部无效**（+1~2% = 噪声级）→ 记录在案，别再试 ✓
3. **视频层才是大头**：片段 121 vs 卡片 70 → **一个视频层 ≈ 50 ms/帧** ✓
   （与之前"模糊背景层占 35%"独立吻合 ✓）

### 与预览的真实差距（结合增量四）

- 预览（真浏览器，4K 1:1）：**合成**每帧上限约 36ms，且**零长任务** ✓ → 合成逻辑本身很便宜 ✓
- 导出（1080P 片段幕）：**121 ms/帧**，其中视频抽帧 ~50ms、编码 ~11ms、其余 ~60ms（离屏光栅+截图序列化）✓
- → **差距集中在"给每帧准备视频素材"** ✓，不在"合成"、更不在"编码" ✓

### 做的改进：片段与画幅同比时**自动不渲染那层模糊背景视频**

- 那层是**第二个视频层** ✓，而当前景 `objectFit: contain` 已铺满画幅（都是 16:9）时它**一个像素都看不见** ✗
- 做法：后端 `MediaProbe.dimensions()` 探素材尺寸 → `PreparedClip.assetWidth/Height` → 片段视图下发 →
  渲染侧纯函数 `needsBlurBackdrop(clip, frameW, frameH)` 判断（容差 1%；**尺寸未知 → 保守渲染** ✓）
- 实现层：`MediaProbe.dimensions` / `PreparedClip`（+2 个兼容构造）/ `RecommendService` 视图透传 /
  `PocClip` 类型 / `clipShot` 条件渲染 / `src/cinema/backdrop.ts` + 3 条单测

### 收益与"零画质代价"的证据

- **耗时：114 → 87 ms/帧（−24%）** ✓（同片段幕同帧区间；另一次独立隔离测到 −35% ✓ → 口径 **−24%~35%**）

## 增量七：局部重渲（用户问「能不能只渲有问题的那一段再重新拼接」→ 拍板「默认保留 / 删任务连产物一起删 / 直接覆盖」）

### 为什么几乎不用新逻辑

分块渲染本来就满足三个前提：① 每块一个独立 mp4；② 续渲会**自动跳过已存在的块**；③ 拼接已证无缝（带 `duration` 清单）。
→ 所以「只重渲某一块」= **删掉那一块的文件 → 触发续渲（只补这一块）→ 重新拼接 → 覆盖原成品**。

### 关键约束（必须讲清，也是本条目的核心）

**只有"不改时长"的修改才能局部重渲**：
| 改什么 | 能否局部重渲 |
|---|---|
| 文字 / 封面 / 标签 / 音量 / 色调等参数 | ✅ 能（时长不变 → 段边界不变） |
| 加删媒体、改片段起止、改各类时长设置 | ❌ 不能（总帧数与段边界全变 → 旧块在新时间轴上对应别的内容）→ 必须整片重渲 |

编辑器拿**当前草稿算出的边界**与快照比对（`editor/rerender.ts` 纯函数 + 4 条单测）→ 一致才放行，不一致给出具体原因（段数变了 / 第 i 个边界位移）。

## 增量十二：同步弹窗**交互重设计**（用户：「方便直观、操作简单没有歧义」）

### 用户连问两个问题，暴露的是我的设计缺陷

1. 「直接同步全部是同步勾选的还是所有的？」→ 答：**所有拉取到的**（不看勾选 ✗）。三重歧义：不看勾选 / 不看「只选 TV」/ 包含**列表没渲染出来的**条目（渲染上限 400 ✗）
2. 「我没看到同步选中的按钮啊？」→ **成立，是我的 bug** ✗：拉取后我把主按钮文案改成「**重新拉取**」，可它实际执行的是"提交勾选项" → **标签在撒谎**，用户根本找不到同步入口 ✗（上一条答复我把内部行为说成有按钮，不严谨，勘误）

### 重设计的三条原则

| 原则 | 做法 |
|---|---|
| ① **一个同步入口** | 底部只有「**同步勾选的 N 部**」；**删掉「直接同步全部」**（它就是歧义源）；N=0 时按钮禁用并显示「未勾选作品」 |
| ② **选择与执行分离** | 「全选 / 只选 TV / 清空」只改复选框，**永不写库**；同步范围**永远等于当前勾选** —— 没有第二种真相 |
| ③ **点之前就知道结果** | 实时预告「将新增 x · 更新 y · 跳过 z」，并直接写在按钮上（N 实时跟勾选变） |

### 布局（编号 = 因果顺序）

```
① 选范围  年份[…] 全选/清空             [拉取候选]   ← 首屏唯一动作（主按钮）
          季度[…] 月份[…]                            ← 拉完后这个降级为次要灰按钮
          （拉取中：第 2/4 段：2024 春… + 进度条）
② 挑作品  共 254 部 · 已选 131/254  [全选][只选 TV][清空]
          将新增 75 · 更新 56
          ┌ 候选列表（内部滚动，紧凑行 + 新增/更新/跳过徽章）┐
③ [取消]                                  [ 同步勾选的 131 部 ]   ← 唯一同步入口
```

**默认勾选** = TV（且排除"命中多个同名"的冲突项）✓ —— 因为 `type=2` 会混进剧场版/WEB/OVA，而"只选 TV"这个工具按钮随时能把整批勾回来 ✓。
