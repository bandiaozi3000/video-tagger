# 2026-08-07 工作日志

## v0.12 渐变环流推荐导出（HTML + 视频 720P/1080P/4K）

**需求缘起**：此前在 `docs/design/photo-wall-D-ring.html` 迭代打磨的「渐变环流推荐页」设计稿（深色霓虹、椭圆轨道自转、飘带入场、自动导览），用户要求**完整写入当前项目**，打通「勾选推荐番剧 → 生成 HTML → 导出视频」整条链路，视频清晰度可选，作为大版本发布。

### 拍板决策（AskUserQuestion 三项）
1. **视频导出实现**：Node + **puppeteer-core** 脚本（后端 `ProcessBuilder` 调 `node render.js`，连系统 Chrome 以 CDP `Page.startScreencast` 录制 + ffmpeg 合成）——不引 Java 渲染库，复用本机 Chrome 保证视觉与浏览器一致。
2. **版本号**：**0.12.0**（不跳 1.0.0）。
3. **清晰度档位**：**720P / 1080P / 4K** 三档。

另承接设计阶段拍板：HTML 模板**移除一切与推荐无关文字**（提示语/生成时间/品牌名/页脚/版本标识/⇪ 顶部按钮），只留「我的番剧推荐」+ 瓦片内容 + 「第 X 部 / 共 N 部」+ 进度条。

### 实现
- **后端**：`CoverService.base64ForCoverPath`（封面 base64 内嵌，防越界/缺失降级）→ `RecommendService.buildHtml`（按 ids 顺序组装：封面/分类路径/标题/备注/状态中文/标签热度 TOP6，HTML 转义防注入，缺失媒体跳过保序）→ `RecommendController`（`POST /api/recommend/html`、`POST /api/recommend/video`，DTO record 反序列化）→ `RecommendVideoService`（ProcessBuilder 编排，20min 超时/产物校验/临时目录清理，时长 = 7 + N×6 + 2s）。
- **脚本**：`backend/scripts/render.js` + `package.json`（puppeteer-core）——`?record=1` 录制模式忽略交互打断、自动导览全程播放，screencast 抓帧 + ffmpeg **CFR 固定帧率**合成；`videotagger.render.*` 配置（scripts-dir 候选兜底解析，IDE 项目根 / mvn backend 双场景可用）。
- **模板**：`templates/recommend.html`——`__SLIDES_JSON__` 占位符注入数据 + `IS_RECORD` 分支开关交互监听。
- **前端**：`index.html` 批量勾选工具栏「导出推荐」按钮 + 导出弹窗（类型 HTML/视频 + 清晰度下拉）+ 下载 toast；`app.js` 绑定导出逻辑（fetch blob → a.download）；`app.css` 新增 `.toast`。
- **版本**：pom 0.11.0 → 0.12.0。

### 测试与验证（实机全链路）
- 单测 **18 例新增**全过（RecommendControllerTest 4 / RecommendServiceTest 8 / CoverServiceTest 6）；排除 IT 全量套件通过。
- **实机验证**（8081 起新代码实例，避免打扰 8080 的 IDE 实例）：
  - `POST /api/recommend/html` 4 部 → 5.5MB 单文件，4 张 base64 封面内嵌，标题/分类/状态/标签齐全。
  - `POST /api/recommend/video` 720P → 21s / 1280×720 / h264 / 解码 OK。
  - 1080P → **21.00s 精确 / 1920×1080 / 60fps** / 解码 OK。
  - render.js 直跑 4K → 3840×2160。

### 关键 gotcha（都曾实锤踩到）
1. **脚本路径**：脚本在 `backend/scripts`，但 IDE 启动后端 **cwd=项目根**（封面 `data/covers` 解析到项目根证明），`scripts-dir` 相对路径两种跑法（IDE 项目根 / mvn backend）指向不同——`RecommendVideoService.resolveScriptsDir()` 按候选兜底，杜绝一种启动方式配置失效。
2. **反序列化陷阱**：`video` 端点 `@RequestBody Map<String,Object>` 把 JSON 数字数组解成 `List<Integer>`，强转 `(List<Long>)` 因擦除不报错、遍历时 ClassCastException——改 record DTO `RecommendExportRequest(List<Long> ids, String resolution)` 由 Jackson 按泛型正确解析。
3. **headless Chrome 分辨率压缩**：`--disable-gpu` 下 Windows 软合成把超大 viewport 宽度 ×0.75 压缩（1920→1440、3840→2880，1280 正常）。去掉 `--disable-gpu` + `--window-size` + `--force-device-scale-factor=1` 后原尺寸输出。
4. **concat demuxer 时长失控**：screencast 帧 ts 差做 duration 的 concat 合成，末帧 duration 语义不可控，1080P 输出 25.88s（目标 21s）。改 **CFR** `-framerate = 帧数/目标时长` 精确还原（21.00s，且帧率回到真实 60fps）。
5. **node 的 `/tmp` 坑**：git-bash 下 node 把 `/tmp` 解析成 `D:\tmp`（不存在）——脚本/测试文件一律用 Windows 绝对路径。

### 修复：勾选框常驻（用户反馈"前端勾选在哪"）
- **问题**：`app.js` renderMediaGrid 勾选框被 `mediaBatchMode` 门控（`${mediaBatchMode ? '' : 'hidden'}`），不进「批量删除」模式看不到勾选框，导出链路无从开始。
- **修复**：勾选框去掉 `mediaBatchMode` 门控常驻显示（封面右上角）；hover 删除 × / 收藏夹 ⇤ 从右上角移到**右下角**（与左下角 ♡ 对称）避免重叠；`process-resources` 同步 target/classes。
- **实机验证**（agent-browser）：媒体页每卡可见勾选框；勾选 2 部 → 「导出推荐(2)」按钮出现；DOM 位置确认勾选框(右上 228,260)与删除 ×(右下 221,433) 不重叠。

## v0.13 推荐导出向导化（独立 tab + 分步 + iframe 预览 + FS API）

**需求缘起**：用户对 v0.12 的导出流程不满意：「流程不太喜欢。推荐希望做成一个单独的工具栏。页面分几个步骤，第一个步骤勾选要推荐的番剧，然后下一个步骤弹窗是主题，接着可先预览生成的html，若没问题。预览html可点击导出视频，再勾选视频标题，格式，清晰度，导出地址等」。

### 拍板决策（AskUserQuestion 四项）
1. **主题** = **标题文案**（文本，渐变环流布局内大标题展示，不新增设计元素）。
2. **预览** = **弹窗内嵌 iframe**（`iframe.srcdoc` 渲染自包含 HTML，无需下载即可看导览）。
3. **导出地址** = **浏览器保存弹窗**（File System Access API `showSaveFilePicker`；用户取消保留原状；非 Chromium 降级默认目录下载）。
4. **入口** = **独立「推荐」tab**（向导内部完成勾选，不依赖媒体页批量勾选）。

### 实现
- **后端**：`RecommendService.buildHtml(ids, title)`——`__TITLE__` 占位符注入标题（空/空白 → 「我的番剧推荐」，HTML 转义）；`RecommendVideoService.render(ids, title, format, resolution)`——格式经 `FORMATS` 映射归一化（大小写不敏感），`render.js` 透传 `--format`。
- **脚本**：`render.js` 新增 `encodeArgs(fmt, out)`——MP4 `libx264 veryfast +faststart` / WEBM `libvpx-vp9 CRF32 + row-mt`。
- **模板**：`templates/recommend.html` 的 `<title>` / `<h1>` 改为 `__TITLE__`。
- **前端**：`index.html` 移除媒体页「导出推荐」工具栏按钮 → 新增第 7 个「推荐」tab + `.wizard-steps` 三步骤条 + 三 pane（勾选 / 主题 / 预览·导出）+ 预览弹窗（iframe）+ 视频导出弹窗（标题/格式/清晰度/位置）；`app.js` 完整向导状态机；`app.css` 向导样式块（步骤条/计数/标题实时预览/弹窗）。
- **版本**：pom 0.12.0 → 0.13.0，ver-chip → v0.13.0。

### 关键 gotcha（实锤）
1. **顶层 `let` 变量不挂 window**：`recommendDstHandle` 是脚本顶层 `let`，`window.recommendDstHandle=…` 注入无效（走了下载分支）——FS 分支必须经 `pickVideoDst()` 成功返回 handle 才会给真变量赋值。agent-browser 里测 FS 分支用 mock `showSaveFilePicker` 返回 fake handle，实测 `write`+`close` 调用链。
2. **agent-browser 点步骤条 ref 指向步骤按钮**而非「下一步」——向导步骤切换用 JS `element.click()` 验证更稳。

### 修复：预览弹窗太小（用户反馈"预览太小都看不到"）

### 修复：导出视频播放卡顿（用户反馈"下载的视频很卡"）
- **排查数据（ffmpeg 实测，2 部 21s）**：
  - 1080P MP4：54.7fps / 765kb/s——内容无跳帧（1148 间隔零跳帧），但帧率低于目标 60、码率偏低。
  - 1080P WEBM：负载高时掉到 **38.1fps**（抓帧率受机器负载影响大，headless Chrome 合成 + JPEG 编码是瓶颈）。
  - **4K**：**18.76fps**（3840×2160 抓帧 JPEG 编码太慢，直接掉到 1/3 帧率）→ 用户导出 4K 必卡。码率 924kb/s 且糊。
- **根因**：抓帧（`Page.startScreencast` JPEG）编码开销拖低推帧率；帧率随负载波动（38~55fps）；VP9 软解 + 低码率放大观感卡顿。
- **修复（render.js + 前端）**：
  1. **抓帧 JPEG 质量 82→70**：编码更快 → 帧率稳定。实测 1080P MP4 **58.8fps**、WEBM **59.1fps**（波动 38→59 稳了）。
  2. **编码码率提升**：h264 `-crf 20`（765→1374 kb/s）、vp9 `-crf 28` + `-cpu-used 2`（915→1789 kb/s），画面少块状伪影。
  3. **4K 降档抓帧**（`render.js` 视口+抓帧 ≤1920 宽再 ffmpeg 放大）：4K 从 18.8→31.6fps（有改善；用户指示「4K 先别管」，保留该逻辑、1080P 不受影响）。
  4. **前端 WEBM 提示**：格式选 WebM 时弹窗内提示「⚠ WebM 播放依赖 VP9 硬解，若卡顿建议改用 MP4」（h264 硬解通吃）。
- 实机验证：前端提示切换正确；1080P 两格式均 21.00s / ~59fps / 码率 1.3~1.8Mb/s。
