## 桌面轨道冻结（政策落规则）

### 需求与决策

- 起点：用户问 Remotion 改造进度 → 追问「只改 web 端、不同步桌面端，日后到某个版本节点再同步」是否可行 → 逐层分析收益/弊端 → 最终收敛为：
  **牵扯桌面的内容能维持不变就不变，但后续开发不再同步维护。**
- 用户拍板：**冻结**（代码保留不删，停止同步维护，将来需要时一次性从 MySQL 全量重建），并要求写进规则。

### 分析结论（支撑这次决策的实测事实）

**架构事实（读码，已核对）**

- 前端只有一份：`backend/src/main/resources/static/` 打进 backend jar；桌面壳 `desktop/main.js:596` 就是 `loadURL('http://127.0.0.1:<port>/')` 加载同一份。**不存在两套前端代码。**
- 桌面在线更新只替换 `backend.jar`（`desktop/update.js` 头注释），不换 jre/node/chrome/ffmpeg；且 `desktop/package.json` 的 `updateUrl` 为空 → **更新功能未启用，桌面用户本就处于滞后状态**。
- 桌面接触面只有三处：静态前端（含 `body.desktop-mode` 布局）、mapper 方言、`application.yml` 默认值。`desktop/*` 全是外壳，web 不 import。
- 双库方言机制 = `config/MybatisConfig.java` 的 `DatabaseIdProvider` + mapper 成对注解；实测 **6 个 mapper / 18 处 / 9 对**（内容全是 `LIKE '%'||?||'%'` ↔ `LIKE CONCAT(...)` 与 `INSERT OR IGNORE` ↔ `INSERT IGNORE`）。
- **`sqlite-jdbc` 有第二身份**：`AnimekoTagService.java:226`、`AnimekoWatchImportService.java:142` 用它当**客户端**读 Animeko 自己的 SQLite 库（现场打标 / 观看导入），单测也拿临时 SQLite 当 Animeko DB 替身。→ 与桌面数据源无关，**不能随"清理桌面端"一起删**。

**日常开发实际跑的是 MySQL（实测）**

- `.idea/workspace.xml:91` → IDEA 启动参数含 `--spring.profiles.active=mysql --server.port=8080`。
- `data/video_tagger.db` mtime = 2026-08-26，而 `data/logs/video-tagger.log` = 2026-09-14 → **SQLite 轨道自 8-26 起未被触碰**。
- 反差：`application.yml:16` 的**默认**数据源仍是 SQLite，`mysql` 只是覆盖 profile。

**既有毛病（本次比对顺带挖出，均为读码/清单比对，未实机跑）**

1. **`MigrationTool` 静默漏表**：基线 `sqlite-schema.sql` 有 39 张表，`MigrationTool` 只迁 36 张，差的正是 `highlight_project` / `highlight_project_item` / `highlight_export`。`git log` 追溯工具从 2026-08-14 建立（16 表）扩到 v0.23（36 表），**highlight 三表从未进过清单**（各版本 grep 命中均为 0）。而 `data/backup/video_tagger_20260904_042357.sql` 里这三表确有数据（INSERT 211 / 153 / 917 字节）→ **8-26 那次全量同步已静默丢掉高光数据，且不报错**（工具只对列出的表做行数校验）。
2. **前端侧栏在说谎**：`index.html:844` 硬编码 `<span ... id="sb-db">SQLite</span>`，`app.js:48` 拼 `'SQLite · ' + n + ' 部媒体'` → 实际连的是 MySQL。

**实测纠正一个想当然**（避免写进文档时出错）

- 用 `node --experimental-sqlite` 实跑：`SELECT CONCAT('a','b')` → **可用**（SQLite ≥3.44 新增 `concat()`，项目 sqlite-jdbc 3.45.1.0 满足）；`SELECT SUBSTRING_INDEX('a,b',',',1)` → **`no such function`**。
- 即 `ClipMapper` 的 `CONCAT` 写法两端都能跑，其注释「SQLite 版」是准确的。起初按老经验判断为「MySQL 专有」是错误的，靠实测纠正。

## Remotion 替换推荐视频渲染链路：设计规格（v0.27）

### 需求与决策

- 用户拍板 3 个前置问题：① **跑在本机**（不追求 Docker/桌面/云端）② **音频直接带原声** ③ **替换成 Remotion**（不是并存）。
- 追问出的第 4 项：现状 BGM 是完整特性（多曲 concat + 模板 BGM 条 UI + 时长对齐 + 「等放完」收尾），而 POC **完全没有 BGM** → 用户选 **(b)**：Remotion 出带原声成片，BGM 混流仍由 Java FFmpeg 负责。
- 版本：**v0.27**（查实 v0.26.0 已于 2026-09-08 发布，CHANGELOG 明写「正式模板录制/导出仍留在 v0.26 后续阶段」；同时收回 v0.26 方案里「暂不引入 Remotion」的约束）。

### 调研到的关键事实（读码，未实机验证）

- 现状链路的**单一替换点** = `RecommendService.buildHtml()`（`RecommendService.java:159` → `readTemplate()` → `normalizeStyle()`）：读 `classpath:templates/recommend-<style>.html`，用 `esc()` / `jsText()` 把数据注入成 JS 字面量，写 `work/recommend.html` → 交 `node render.js` 用 puppeteer 实时抓帧 → 出**静音**视频 → Java ffmpeg 混 BGM（`-stream_loop -1` + `-shortest`，`RecommendVideoService.java:321-332`）。
- `/preview`（`app.js:4556`）、`/html`（`app.js:4591`）、视频路径三个入口**共用** `buildHtml()`；`/video`（`app.js:4656`）与任务队列接口可保持签名不变 → 前端零改动的路径是存在的。
- **素材被强制去音轨**：`RecommendClipSourceService.java:106` 用 `-an` 生成无声素材 → 要「直接带原声」**必须改这里**，这是 (b) 方案的硬前置。
- **时长权威冲突**：Java 现在算 `durationSeconds`（`Durations` 五段秒数 + clip 秒数 + BGM 收尾余量），而 Remotion POC 的 `buildScenePlan()` 用硬编码常量（`scene-plan.ts:5-8`：opening 3s / clipInfo 3s / infoOnly 5s / ending 3s）→ 规格里定为「`buildScenePlan()` 唯一权威，`Durations` 经 `RenderInput` 传入」。
- **风格搬迁的真实工作量**：`recommend-chapter.html` 实测 69KB，内含 23 处 `transition:`、5 处 `@keyframes`、11 处 `setTimeout`、4 处 `setInterval`、2 处 `rAF`、1 `<video>`、1 `<audio>` —— 这些驱动方式在 Remotion 逐帧模型下全部要改写（CSS/DOM 可照搬，因为两边都是 Chrome）。
- **`clip` 样式**：`normalizeStyle()` 里 `chapter`/`clip` 都是正式模板，且共用一个 `render()` 方法 → 替换动作天然会同时影响两者，规格里改为「先只换 chapter」并列为待确认项。
- `RecommendExportRequest` 有 **25+ 个模板参数**（`bg*`、`perScreen`、`openingSpeed`、`bgmScale/X/Y` 等）→ 规格里出了「参数支持矩阵」，因为不支持 = UI 出现死开关（功能倒退），必须显式拍板。

### 产出

- 新建 `docs/superpowers/specs/2026-09-17-video-tagger-v027-remotion-recommend-replace-design.md`（17 节）：目标 / 已确认决策 / 替换范围 / 现状链路 / 目标架构 / 数据契约 / 风格对齐 / 音频与 BGM / 渲染调用 / 预览接线 / 参数矩阵 / 部署边界 / 不做 / 验收标准 / 风险 / **待确认 6 项** / 变更记录。
- 按项目流程：**规格待用户审阅批准；批准前不写执行计划、不动代码**（用户已选 C = 先出规格）。

### 验证

- 写规格前的调研均为只读（read/grep），未改任何实现代码。
- `git status --short` 复核本次新增/修改文件范围。

### 遗留 / 待用户决定

- 规格 §16 的 6 项：`clip` 是否同期替换 / 参数支持矩阵 / `/preview` 与 `/html` 处置（P1/P2/P3）/ BGM 是否要 ducking / 旧链路（`render.js` + puppeteer）是否同期删除 / Remotion 许可证与商业分发。
- 未验证项：1080P/4K 渲染耗时（POC 只测 720P）、BGM 与原声 `amix` 的实际听感、`amix` 在无音轨产物上的失败分支（仅从 ffmpeg 语义推断）。

### 可迁移的学习点（Remotion 部分）
- 换渲染引擎前先找「**单一替换点**」：本项目是 `buildHtml()` 一个方法同时被预览/分享/导出三个入口共用。找到它，才能得出「`/video` 接口签名不变 → 前端零改动」这种低成本结论。
- 「保持风格」可行性的真正判断依据是**两边是不是同一个渲染引擎**。旧链路是 Chrome 实时抓帧，Remotion 也是 Chrome 逐帧截图 → CSS/DOM 能照搬，只有**驱动方式**（`setTimeout`/`rAF`/CSS `transition`/`@keyframes`）必须改写。反之，如果旧模板是 Canvas 或原生渲染，结论就完全不同。
- 接入新引擎时最容易漏的是**不可见的输入面**：不是视觉，而是那 25+ 个模板参数。支持的少了不是“中性”，而是 UI 里多一个“调了没效果”的死开关 → 属功能倒退，必须显式拍板。
- 旧链路里所有“补丁数值”（如“总时长 + 最长单曲 + 5 秒”）往往是**旧引擎缺陷的补偿**，不是业务规则。换引擎时要逐个问“这个补丁还需要吗”，否则会把旧缺陷一起搬过来。

### 踩的坑（报错与根因）

1. **单测期望值两次算错**：`speedToFrames(50,30)` 我按注释写 18、实际 22（公式 `36 - 0.28×speed`）；`speedToFrames(50,60)` 我写 36、实际 44。报错原文 `AssertionError: expected 22 to be 18`。根因是我手算了公式却没跟注释对齐。修法：统一成公式真实值，注释同步（0→36 / 50→22 / 100→8 帧）。
2. **`bgRotationSec` 两次被判“未生效”**：
   - 第一次 frame 取末帧（692），根因是巧合：`floor(692/240)=2` 与 `floor(692/30)%3=2` **恰好同一张图**。改到资料卡中点（135）后仍相同 →
   - 真正根因：**`MediaInfoScene` 的不透明渐变（`linear-gradient(115deg, #111416 …)`）把背景层完全盖住**——这是真实视觉缺陷，不是测试问题。修法：背景层存在时该渐变 `opacity: 0.35`。
   - 这一坑直接证明“先建判定口径”的价值：没有它，“支持了”只是我自己说好。
3. 环境旧坑重现（已记于上文）：`du -sh` 在本机输出的是**文件数**而非体积，别用它估打包体积。

### 可迁移的学习点（参数验证）

- 验收“参数支不支持”必须给出**可判定口径**。本次用的是：同帧同输入、只改一个参数、字节比对，再加一道**确定性对照**（同输入两渲字节必须一致）——否则“字节不同”可能只是噪声。

### 发现并修复的生产 bug（实测）

**`recommend-chapter.html` / `recommend-overview.html` 缺 `</style>` 闭合标签 → 整页空白。**

| 证据 | 结果 |
|---|---|
| `grep -c '</style>'` | 两个文件都是 **0**（其余四个模板都是 1） |
| `git log -S '</style>'` | **空** → 该标签从未存在过（非近期回归） |
| Chrome 探针（chapter） | `bodyKids=0`、`scripts=0` → 文档体没有任何内容，脚本根本不执行 |
| 补上 `</style>` 后再探针 | `bodyKids=4`、`hero=true` → 恢复正常 |

根因：HTML tokenizer 的 RAWTEXT 状态只认 `</style>` 结束；`</head><body>…` 全被当成样式表文本吞掉，body 永远为空。

影响面：`normalizeStyle()` 把 **`chapter`（默认）以及 `stream`/`overview`/未指定都归到 chapter** → 只有显式选 `clip` 才正常。

处置：两个模板各补一行 `</style>`（共 2 行，**本次唯一改动的生产文件**），已实测 chapter 恢复渲染。

1. `ffprobePath()` 原来只认 ffmpeg 同目录 → 本机 `~/.local/ffmpeg/bin` 只有 ffmpeg → 探测恒失败（按“有原声”处理）→ 每次导出都白试一次 amix。现支持 `RENDER_FFPROBE_PATH` 配置。

## Player 预览修复完成（同日第六次追加）：可用了

用户：「继续修」。两处缺陷均定位并修好，实测通过。

### 根因与修法

**① 封面没进 RenderInput（卡片无封面）**
- 根因：`buildRenderInput` 固定用 `resolveCoverDataUrl(d, "embed")` → `coverService.base64ForCoverPath(d.coverPath())` 返回 null（`coverPath` 是带 `/covers/` 前缀的路径，与该方法的预期不一致）→ `coverAssetPath` 被跳过。
- 修法：`buildRenderInput` 新增 `coverMode` 参数 —— **渲染用 `embed`（data URI，无头环境自足），浏览器预览用 `url`（`/covers/x.jpg`，宿主直接托管）**；新增 `src/asset-url.ts` 统一拼装，让 **根相对路径（`/…`）也透传**，不再被拼上 `assetBaseUrl`。
- 实测：`.sc-poster img` = 1，`src=http://127.0.0.1:18099/covers/7492.jpg`，`naturalWidth=480`（真解码了）。

**② 资料卡被顶出视口（`y=-341`）**
- 根因：Player 容器只给了 `flex:1` + `height:'100%'` → **Player 内部包装层算出高度 0**（探针实测父链上有一个 `h=0; position:relative` 的 div），于是它内部绝对定位的画布（720 高）从静态位置向上溢出 → `__remotion-player` 的 `y=-341`。
- 修法：容器给**确定高度** —— `aspectRatio: <plan.width>/<plan.height>` + `maxHeight: 78vh`，页面改为居中布局。
- 实测：`.hero` / `.story-card` 均 `y=69`、`h=657`（在视口内）。
