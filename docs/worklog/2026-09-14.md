## 回收站释放 Bangumi 关联

### 需求与决策

- 用户反馈：媒体已关联 Bangumi 后移入回收站，其他媒体搜索同一条目仍显示“已关联其他媒体，不可选”。
- 确认语义：回收站保留本地媒体、集、片段与标签，但释放 Bangumi 外部关联；恢复后不自动恢复 Bangumi 关联，需手动重新关联。
- 这样避免回收站媒体继续占用稳定 Bangumi ID，也避免复用旧 `external_episode` 桥接后把新媒体同步到旧集。

### 根因

- `MediaService.trash()` 过去只写 `media.deleted_at`，`external_work.media_id`、`external_episode` 和 `external_relation` 保持不变。
- 后端候选由 `external_work.media_id` 判断稳定关联；前端旧逻辑还会把任意带 `targetMediaId` 的同名候选禁用。
- 后者会把 `matchType=TITLE` 的人工确认建议错误显示成“已关联其他媒体”。

### 实现

- `MediaService.trash()` 在同一事务内调用现有 `purgeExternal()`，清理外部作品、集桥接和关联作品缓存；`trashBatch()` 复用该路径。
- 新增 MySQL `V33__release_metadata_for_trashed_media.sql`、SQLite `migration-sqlite/v15.sql`，按关系 -> 集桥接 -> 外部作品的依赖顺序清理既有回收站脏数据；测试资源同步 v15。
- SQLite 迁移器对 v15 的“相关表/列不存在”严格限定为可跳过，兼容极早期残缺库；其他 SQL 错误仍中止迁移。
- 关联弹窗只在 `matchType=EXTERNAL_ID` 且目标是其他媒体时禁用候选；同名 `TITLE` 候选保持可选。
- 单删、批量删除和详情删除提示明确说明：Bangumi 关联会释放，恢复后需要重新关联。

### 验证

- TDD：新增 `MediaServiceIT.trashReleasesBangumiBindingAndBridgeCache`，先在旧实现上失败（`external_work` 仍存在），实现后通过。
- 新增 SQLite `v14TrashMetadataIsReleased`：v14 历史库迁移到 v15 后，回收站媒体的三类外部记录被删除，活跃媒体记录保留。
- 定向 MySQL 集成测试、SQLite 迁移测试、全量 `mvn test` 均通过；前端 `node --check` 与 `git diff --check` 通过。
- 真实 8080 验收：重启后，回收站媒体 `7493` 的元数据接口返回 `work=null`；真实页面搜索 Bangumi #3291，候选从错误的“不可选”变为可勾选；测试媒体 `7494` 成功关联 #3291 并同步 26 集，随后 `DELETE /api/media/7494` 返回 204 且元数据变为空，永久清理返回 204，详情查询为预期 404。
- 浏览器自动化在“关联并同步”长请求等待阶段两次断开，但已完成页面候选可选性验证；实际关联和删除使用同一 8080 API 验证完成。

## Remotion 多媒体混合推荐模板最小 POC（同日续）

### 目标与授权

- 用户拍板 1A/2C/3A/4C/新增并存，并要求本次只验证 Remotion 路线是否走得通。
- 设计规格：`docs/superpowers/specs/2026-09-14-video-tagger-remotion-multi-media-recommend-poc-design.md`；执行计划：`docs/superpowers/plans/2026-09-14-video-tagger-remotion-multi-media-recommend-poc-plan.md`。

### 环境事实（本次实测）

- Node v22.20.0、npm 10.9.3；Remotion 全部 `@remotion/*` 锁定 4.0.524。
- 系统 PATH 无 ffmpeg/ffprobe，本机可用 `/d/Tool/LosslessCut/resources/ffmpeg.exe` 与同目录 `ffprobe.exe`；POC 脚本按参数接收，不硬编码进业务代码。
- Remotion 首次渲染自动下载 Chrome Headless Shell 到 `backend/remotion/node_modules/.remotion`，**占约 521MB**——这是后续桌面打包必须单独评估的体积项。

### 实现

- 新独立工程 `backend/remotion/`（不改根工程、不改旧模板、不改 `RecommendVideoService`）。
- 纯函数 `buildScenePlan(input)`：媒体按 `ids` 顺序、Clip 按每媒体 `order` 顺序生成帧级场景；开场 3s、有 Clip 资料卡 3s、无 Clip 资料卡 5s、结尾 3s；Clip 用准备后时长，已裁切素材从第 0 帧播放。
- Composition `MultiMediaRecommendPoc`：开场 / 媒体资料卡 / Clip / 结尾四类场景，Player 与 renderer 共用同一组件与同一场景计划。
- 本地 Player 页面（`serve-player.ts`，Vite，资源根固定 `poc/`，路径越界拒绝）+ Node renderer（`render-poc.ts`，bundle → selectComposition → renderMedia，输入校验后本地 HTTP 提供资源）。
- TDD：`scene-plan.test.ts` 先红灯（`buildScenePlan` 未实现）后转绿 4/4，覆盖资料-only 媒体不生成 Clip 场景、媒体/Clip 顺序、帧数总和、非法输入拒绝。

### 真实样本与验收（8080 真实库数据）

- 样本：A=少女与战车（1 个 Clip，有声）、B=铃铛猫娘 夏季特别篇2000（无 Clip，资料-only）、C=现视研 2代目（1 个 Clip，素材无音轨）。素材用本机已存在的 `data/video-assets/...asset-18.mp4` / `asset-21.mp4` 裁成 5 秒级短样本。
- 场景计划实测：`90 + 90 + 153 + 150 + 90 + 150 + 90 = 813` 帧，顺序 `OPENING → INFO(5609) → CLIP(179) → INFO(7475) → INFO(5520) → CLIP(180) → ENDING`。
- 两次相同输入渲染：均 813 帧、场景与 Clip 顺序一致；冷启动 168.5s、热启动 106.9s，产物 3.47MB。
- ffprobe：h264 1280×720、30fps、AAC 2ch、时长 27.100s（= 813/30，误差 0）。
- 音频实测（volumedetect）：有声 Clip 段 mean -31.4dB / max -17.0dB；资料-only 段与无声素材段均 -91.0dB。
- 成片逐场景抽帧：资料卡、Clip 179（真实战车道画面 + `#01 少女与战车` / `CLIP 179` / 第 1 集标题）、资料-only 媒体 B（海报 + 年份季度 + 简介 + 标签 + “资料推荐 · 本次未选片段”）、结尾（3 媒体海报墙 + 3/2/2 统计）全部正确。
- Player 验收：浏览器打开可播放；播到 50% 时 DOM 显示资料-only 场景同一内容，且该场景 `video` 元素数为 0，确认无空视频场景；Player 与成片结构一致。
- 旧链路冒烟：`node --check app.js` 通过；`RecommendSingleServiceTest` exit 0。

### 结论

**通过（POC 路线可行）**，但为 POC 级结论，尚不代表可以进入生产接线。

### 遗留 / 未验证（不粉饰）

- **真实渲染未覆盖“同一媒体 2 个 Clip”分支**：8080 真实库中同一媒体只有 1 个可复用短素材，为避免伪造数据库不存在的 Clip，真实样本用了跨媒体 1+1；该分支只由单测覆盖，建议用户指定一部有 2+1 段可复用素材的媒体后补一次真实渲染。
- Remotion 自带 Chrome Headless Shell 约 521MB，桌面打包与在线更新策略未评估。
- 未验证：BGM、1080P/4K、跨媒体切换动画打磨、Electron 打包、`calculateMetadata` 与 Player 输入不一致时的行为。
- 渲染耗时（冷 168s / 热 107s，27 秒成片、concurrency=1）尚未与现有 FFmpeg 链路做同条件对比。
- `webpack.cache.PackFileCacheStrategy: Caching failed for pack` 在两次渲染均出现，暂判为无害告警，未深挖。
- 按计划本应删除真实素材样本；本次**保留**在 `backend/remotion/poc/media/` 与 `output/`（均已在 `.gitignore`），方便用户自行审阅，未提交。
