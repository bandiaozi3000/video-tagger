## MySQL 数据卷损坏与数据恢复（docker 事故 + 排障）

**事故**：Docker 异常退出 → 数据盘 ext4 损坏 → VHDX BAT（块分配表）被清零 → MySQL 数据"看起来全丢"，且 `main` 目录损坏 + D 盘 exFAT dirty，Docker Desktop 彻底起不来。

**恢复全流程**（desktop 项目三个连续会话）：
1. 字节级扫描 123G 旧盘：定位 binlog 魔数 `fe 62 69 6e` + `video_tagger` 字符串 → 提取 28 个 binlog（8/12~8/25，2.8G）到 `D:/recovery/binlogs/`；InnoDB 页扫描价值低放弃。
2. binlog 单独重放有限（DML 依赖前置状态）→ **转折**：发现 `data/backup/video_tagger_20260813.sql`（8/13 完整备份）→ 导入备份 + 重放 binlog_13~28 补齐 → **恢复 8367 行**（media 5528 等），导出 `D:/recovery/video_tagger_final.sql`（45M）。
3. `chkdsk D: /f` 修复脏盘（用户拍板"先修盘"）→ 删除损坏 main 目录 → Docker Desktop 恢复（引擎 29.7.2）。
4. `docker compose up` 拉起 mysql/milvus/etcd/minio/attu，导入 final.sql，行数核对一致。

**遗留项与处理**：
- **schema 落后**：恢复的备份是 8/13 快照，缺 V20（clip end_sec）+ V23（metadata library）→ 本机 mvn + mysql profile 启动，Flyway 以 `SPRING_FLYWAY_OUT_OF_ORDER=true` 补跑。
- **乱码疑云**：导入后部分 OMOFUNA 标题 SELECT 显示 `?` → **实为 `docker exec` 默认 latin1 会话的显示假象**；表列是 utf8mb4、数据字节正确（`--default-character-set=utf8mb4` 连接即正常），应用 JDBC 已带 `characterEncoding=utf8`，待应用层验证确认。
- 旧 123G 数据盘已删除（内含 minio 原始文件，已确认不需要）。

**技术复盘**：完整时间线/原理/教训 → `docs/learn/technology.md`《Docker MySQL 数据卷损坏与数据恢复完整复盘》。

**知识沉淀**：Flyway 基本原理科普（迁移脚本命名 / flyway_schema_history 账本 / outOfOrder / checksum / baseline / 双库对照）→ `docs/learn/tech-basics.md`《Flyway（数据库版本控制 / 迁移工具）》。

- **坑（必看）**：Spring Boot fat jar **不能** `java -cp jar com.X` 直接跑非 Spring 的 main——类在 `BOOT-INF/classes/` 下；需用 PropertiesLauncher：
  ```bash
  java -cp target/video-tagger-backend-0.18.2.jar \
    -Dloader.main=com.videotagger.migration.MigrationTool \
    org.springframework.boot.loader.launch.PropertiesLauncher \
    "--mysql-url=jdbc:mysql://localhost:3306/video_tagger?..." \
    --mysql-user=root --mysql-pass=root123456 --sqlite=D:/learn/myLearn/video-tagger/data/video_tagger.db
  ```
- **桌面版数据目录**：`desktop/main.js` 确认桌面版与 Web 共用项目根 `data/`（`VT_DATA_DIR` 可覆盖），故同步后的 `data/video_tagger.db` 即桌面版数据源。

- **范围**：仅备份 MySQL `video_tagger`，不处理 SQLite、Milvus、封面或导出文件。
